Adaptive thinking/Prompt caching

들어가며 — AI의 답을 연구의 근거로 바꾸려면

AI는 큰 저장소에서 관련 파일을 찾고, 긴 로그에서 원인 후보를 좁히고, 논문의 방법을 prototype code로 옮기는 일을 빠르게 해낸다. 문제는 무엇을 보고 그런 판단을 했는지가 그만큼 잘 남지 않는다는 데 있다.

기록이 없어도 당장은 편하다. 답은 매끄럽고 수정안까지 붙어 있으니, 그대로 고치고 다음으로 넘어가면 된다. 그러나 몇 달 뒤 심사 의견에 답하려고 결과를 다시 꺼내면, 그 숫자가 어떤 조건에서 나왔는지 아무도 모른다.

그래서 이 책은 답을 받은 자리에서 무엇을 보았고 무엇을 실행했는지를 파일로 남기는 법을 다룬다.

비싼 모델도 서비스 조건까지 통제할 수는 없다

성능이 좋은 상용 모델에 비용을 더 들이면 도움이 될 수 있다. 다만 더 비싼 구독이 언제나 같은 품질을 보장하지는 않는다.

품질은 모델 성능뿐 아니라 사용자가 모두 통제할 수 없는 동작 조건에도 영향을 받기 때문이다. 상용 구독은 폐쇄형 서비스여서, 공급자는 실제 매개변수 수, 요청을 처리하는 backend, 앞에 붙는 system prompt를 제한적으로만 공개한다.

공개된 사례도 있다. Anthropic은 2026년 4월 Claude Code postmortem에서 직전 한 달 동안 보고된 품질 저하의 원인을 밝혔다. 한 요청의 추론량을 정하는 기본값의 변경, 이전 추론을 지우는 캐시 최적화의 버그, 답을 짧게 내도록 유도한 system prompt다.

세 변경 모두 공급자 쪽에서 이루어졌고, 사용자가 그날 답이 왜 달라졌는지 알아내기도 어려웠다. 구독 등급을 올려도 이 성질은 그대로다.

그러므로 사용자가 통제할 수 있는, 모델 바깥의 작업 조건부터 붙잡는다.

다만 공급자가 바꾸는 조건 가운데 일부는 문서에 버전과 수치로 공개된다. 버전이 올라가면 그 수치도 함께 바뀌므로, 이런 값은 확인한 날짜와 함께 부록 G의 「Claude의 Adaptive thinking과 Prompt caching」에 모아 두었다.

자체 서버만으로 연구 환경이 완성되지는 않는다

성능이 좋은 모델을 자체 서버에 올리면 공급자의 routing이나 quota 변화에는 덜 흔들린다. 작업 조건의 나머지는 여전히 연구실이 직접 꾸려야 한다.

상용 서비스의 품질은 모델 가중치와 그 주변 설정이 함께 정한다. 어떤 모델을 고르는지, system prompt에 무엇을 넣는지, 긴 대화를 어떻게 줄이는지, 무엇을 캐시에 남기는지, 어떤 도구를 부르는지, 어떤 자료를 찾아 붙이는지가 모두 답을 바꾼다. 가중치를 우리 서버에 올려도 이 항목들은 우리가 정해야 한다.

외부 자료를 가져와 쓰는 방식도 여러 설계 선택으로 나뉜다. REALM은 자료 검색 과정을 사전 학습 단계부터 모델과 함께 학습시켰다. DPR은 질문과 문서를 같은 벡터 공간에 넣어 BM25 같은 단어 일치 검색보다 정확하게 찾았다. 이어 RAG는 검색한 문서를 생성 모델의 입력에 붙였다. FiD는 여러 문서를 한꺼번에 입력받도록 구조를 넓혔다. RETRO는 검색 데이터베이스를 수조 토큰 규모로 키웠다. Atlas는 소수 예시(few-shot) 조건에서도 검색 증강이 효과가 있음을 보였다.

이 연구들은 모델 가중치와 함께 자료를 찾아 모델에 읽히는 방식도 설계 대상으로 다뤘다.

모델이 바깥에서 끌어온 자료를 읽는 곳은 context window인데, 이곳에도 손댈 부분이 있다. 창에 넣는 토큰이 늘어날수록 모델이 그 안에서 필요한 내용을 정확히 되짚는 능력이 떨어진다. Anthropic의 Effective context engineering for AI agents는 needle-in-a-haystack 방식의 평가에서 드러난 이 현상을 context rot이라는 이름으로 소개했다.

일반적인 dense self-attention에서는 각 토큰이 다른 토큰과의 관계를 계산하므로, 토큰이 n개일 때 관계의 수는 n² 규모로 늘어난다. Anthropic은 문맥이 길어질수록 모델이 이 관계를 포착하는 능력이 얇게 퍼지고, 학습 데이터에는 짧은 시퀀스가 더 흔해 긴 문맥을 다룬 경험이 적다고 설명한다. 그리고 이 한계를 attention budget에 빗댄다. 실제 성능 저하는 모델과 과제에 따라 확인해야 한다.

따라서 창을 채우기보다 원하는 결과를 내는 데 필요한 가장 작은 자료 묶음을 고르고, 그 안의 신호를 분명하게 만든다.

연구실에서는 web-scale index를 만들기보다 다룰 자료의 경계를 분명히 정하는 일이 먼저다. 논문 PDF, code path, 실험 로그, dataset 규약, 심사 의견을 어떤 단위로 나눌지 정한 다음, 질문을 관련 자료와 연결한다.

자료의 경계를 정하는 일과 그 범위 안에서 직접 작업하는 일에서 사람과 에이전트의 역할이 나뉜다. 실제 세션 40만 개를 살핀 Anthropic의 사용 분석에서도 같은 역할 구분이 나타났다. 그 자료는 1부에서 따로 읽는다.

이 역할 분담을 매번 즉석에서 다시 정하지 않으려면 에이전트가 따라갈 작업 지침이 필요하다. 이 책의 절차는 그 지침을 저장소의 AGENTS.md, project memory, 실험 기록, 주장·근거 표에 나누어 적는 방법이다.

연구용 AI 하네스는 여섯 요소로 나뉜다

이 책이 만들려는 작업 구조를 한 단어로 부르면 하네스다. 말에 채우는 마구나, 몸에 매어 줄과 고리를 거는 장비를 가리키는 말이다.

2026년 연구는 에이전트를 기반 모델에 실행 하네스를 붙인 시스템으로 보고, 그 하네스를 여섯 요소로 나누었다. 무엇을 보여 줄지(관측), 그중 무엇을 이번 호출에 넣을지(문맥), 어떤 주기로 돌리고 언제 멈출지(제어), 무엇을 실행하게 할지(행동), 무엇을 남길지(상태와 산출물), 무엇으로 확인하고 무엇을 막을지(검증과 통치)다.

여섯 요소 가운데 네 요소는 연구 기록과 직접 맞닿아 있다. 관측 영역에는 로그·diff·스크린샷을 모은다. 문맥 영역에서는 작업에 필요한 정보를 고른다. 상태와 산출물 영역에는 체크포인트와 추적 내역을 쌓는다. 검증과 통치 영역에서는 테스트와 감사 기록으로 정합성을 확인한다. 이렇게 남겨 둔 기록이 하네스의 뼈대가 된다.

AutoExperiment의 논문 재현 실험에서는 핵심 함수 하나를 지운 과제를 GPT-4o로 풀게 했다. 과제에 딸린 모든 실험의 결과가 원래 코드의 결과와 상대 오차 5% 이내이면 성공으로 셌다. 정해진 세 걸음을 순서대로 밟는 방식의 성공률은 8.3%였고, 같은 모델이 환경의 응답을 보고 다음 행동을 정하는 방식에서는 35.3%였다. 모델은 그대로이고 하네스를 바꾼 비교다.

무엇을 늘렸을 때 효과가 나는지도 달랐다. 같은 연구의 별도 실험에서 추론 토큰 예산을 늘린 고정 상호작용 방식의 최고 성공률은 o1에서 22.2%, o3-mini에서 27.8%였다. GPT-4o가 환경과 주고받을 수 있는 횟수를 늘린 방식은 약 35%까지 올랐다. 모델과 실행 방식이 함께 다른 비교이므로 증가분을 상호작용만의 효과로 볼 수는 없지만, 이 과제에서는 긴 추론뿐 아니라 실행 결과를 보고 고칠 기회도 중요했다.

이 책은 이 여섯 요소를 연구실의 작업에 적용한다. 대체로 1부는 문맥·상태와 산출물, 2부는 관측·검증과 통치, 3부는 제어·행동에 해당한다.

AI가 낸 아이디어의 우위는 실행 뒤 사라졌다

하네스가 필요한 이유는 AI가 잘하는 단계와 근거가 마련되는 단계가 서로 엇갈리기 때문이다.

Si 등은 LLM이 새로운 연구 착상을 낼 수 있는지를 사람과 비교해 측정했다. 100명이 넘는 NLP 연구자를 모아 착상을 쓰게 하고, 사람의 것과 모델의 것을 섞어 출처를 모르게 심사하게 했다. 새로움에서는 모델 쪽이 사람 전문가보다 높았다(p < 0.05). 실현 가능성은 조금 낮았다.

같은 연구진은 그 착상들을 실제로 실행하는 후속 연구로 나아갔다. 전문 연구자 43명에게 착상을 무작위로 배정해 평균 103시간 동안 구현하게 했다. 연구자들은 결과를 4쪽 분량의 논문으로 작성했고, 다른 전문가들이 출처를 모른 채 심사했다. 실행 전후의 점수를 대조한 결과, 모델이 낸 착상은 네 항목(새로움·흥미·효과·종합) 모두에서 사람의 착상보다 점수가 더 많이 떨어졌다(p < 0.05). 실행 뒤 평균 점수는 어느 항목에서나 사람의 착상이 높았지만, 착상 43개를 각각 독립 표본으로 본 비교에서 최종 점수 차이는 통계적으로 유의하지 않았다.

이 두 연구에서 모델의 강점은 근거가 서는 자리보다 앞쪽에 있었다. 착상 평가에서 높게 받은 점수가 사람이 구현한 뒤의 평가까지 이어지지는 않았다. 구현은 사람이 맡았으니, 모델이 직접 실험하는 능력은 이 비교로 재지 않았다. 착상의 출처가 무엇이든 실제 조건에서 돌려 숫자를 얻고, 그 숫자로 말할 범위를 정해야 한다. 하네스는 이 실험과 검증 과정을 돕는 구조로 쓴다.

착상 후보 가운데 무엇을 할지는 연구자가 고른다

모델은 하나의 질문에도 그럴듯한 착상 후보를 여럿 내놓을 수 있다. 그러나 그중 무엇이 해 볼 값어치가 있는지는 질문한 연구자가 정해야 한다.

앞선 착상 연구의 저자들도 자기 시스템의 한계로 출력의 자기 평가가 약하고 생성 결과의 다양성이 낮다는 점을 들었다. 저자들의 분석에서는 착상을 많이 뽑을수록 새것은 늘지 않고, 앞서 낸 것을 말만 바꾼 것이 늘어났다.

논문 재현 과제에서도 생성 능력과 선택 능력의 격차가 수치로 확인된다. GPT-4o에게 동일한 문제를 5회 반복해 풀게 했을 때 적어도 한 번 정답을 맞힌 비율은 48.2%였다. 한 번만 시도했을 때의 정답률은 35.3%였다. 자기가 낸 다섯 답안 가운데 하나를 고르게 하자 정답률은 37.6%였다. 다섯 번 시도에 정답이 섞여 있는 경우가 많았는데도, 스스로 고른 결과는 한 번 시도보다 2.3%p 높은 데 그쳤다.

스스로 고쳐 쓰게 하면 답이 나빠지기도 한다. 답을 낸 뒤 스스로 검토하고 다시 답하게 한 연구에서는 GPT-3.5의 GSM8K 정확도가 75.9%에서 두 번 검토한 뒤 74.7%로 내려갔다. 전체 문제 가운데 맞던 답을 틀리게 바꾼 경우는 8.8%, 틀린 답을 맞게 바꾼 경우는 7.6%였다.

같은 연구는 조건 하나만 바꾸어 다시 측정했다. 정답을 확인할 수 있는 외부 판정자가 답이 아직 틀렸다고 알려 줄 때만 다시 풀게 하자 75.9%가 84.3%로 올랐다. 절차는 그대로였고, 외부의 오류 신호 하나만 더해졌다.

모델이 만들어 놓은 답 가운데 무엇이 맞는지 가리려면 외부의 판정 기준이 필요하다. 그 기준을 적용하려면 당시의 입력과 결과가 기록으로 남아 있어야 한다.

그래서 좁히는 일은 사람 쪽에 남는다. 이 책의 절차는 매번 어디까지 말할 수 있는가를 묻는다. 이 물음으로 많은 후보를 실행 가능한 범위까지 좁힌다. 뒤에 나오는 규칙은 모두 그 물음에 답할 재료를 남기는 방법이다.

재현 과제에서 AI의 실행 한계가 드러났다

재현 과제는 착상을 제외하고 모델의 실행 능력을 따로 측정한다. 이미 나온 논문을 주고 그 결과를 다시 만들게 하기 때문이다.

PaperBench는 ICML 2024 구두·스포트라이트 논문 20편의 결과를 재현하게 했다. 논문마다 재현 과정을 잘게 나누어 채점표를 만들자 개별 채점 항목은 8,316개가 됐다. 가장 높은 평균 재현 점수는 오픈소스 스캐폴딩을 붙인 Claude 3.5 Sonnet (New)의 21.0%였다. 같은 과제 일부를 기계학습 박사들에게도 시켜 보니 모델은 아직 사람을 넘지 못했다.

분야를 넓혀도 비슷하다. CORE-Bench는 전산·사회과학·의학 논문 90편에서 과제 270개를 만들고 난이도를 셋으로 나눴다. GPT-4o와 GPT-4o-mini로 돌린 에이전트 가운데 가장 어려운 층의 최고 정확도는 21%였다.

코드만 떼어 놓은 과제에서도 같은 실행 한계가 드러난다. ResearchCodeBench는 2024~2025년 논문 20편에서 각 논문의 새로운 대목만 골라 과제 212개를 만들었다. 저장소 20개 가운데 13개는 첫 커밋이 평가한 모델들의 학습 컷오프보다 늦어, 학습 자료에 들어갔을 가능성이 낮다. 가장 잘한 Gemini-2.5-Pro-Preview가 37.3%였고, 40%를 넘긴 모델은 없었다.

난이도를 단계별로 바꾸어 측정한 사례도 있다. AutoExperiment는 재현이 이미 확인된 논문 넷의 저장소에서 핵심 함수를 지운 뒤 채워 넣게 했다. 하나를 지웠을 때 GPT-4o는 35.3%였으나 둘을 지우자 8.5%로 떨어졌다. 다섯을 지우자 대부분의 모델에서 사실상 0이 됐다.

지운 함수가 많아질수록 논문 본문을 읽게 한 쪽과 읽게 하지 않은 쪽의 차이는 벌어졌다. 하나를 지웠을 때는 35.3%와 34.1%로 거의 같았지만, 넷을 지우자 본문이 없는 쪽은 완전히 실패했다. 코드가 충분히 남아 있을 때는 코드가 절차를 보완하지만, 빠진 부분이 많아질수록 본문에 적어 둔 설명이 필요해진다.

이 재현 과제들이 보고한 실패 원인에는 공통점이 있다. 실행 시간이 부족하거나 의존성과 데이터 정렬에서 막힌다. 논문 본문만 보고 절차를 다시 세워야 할 때는 빠진 절차, 방법에서 벗어난 실행, 중간에 깨지는 환경이 실패 사유로 꼽힌다.

이 목록은 2부에서 만들 최소 기록의 항목과 거의 겹친다. 재현의 난도는 방법 자체의 난도에, 그 방법을 돌리는 데 필요한 정보가 얼마나 기록됐는지가 더해져 정해진다.

자동 연구가 낸 성과에도 사람의 검증은 필요했다

2025년 11월에 공개된 Kosmos는 한 번 실행할 때 에이전트 롤아웃을 200회 넘게 돌리고, 평균 42,000줄의 코드를 실행하며 논문 1,500편을 읽는다. 함께 일한 연구자들은 20주기로 이루어진 한 번의 실행을 자신의 기준으로 평균 6개월치 작업으로 보았다. 독립 과학자들이 보고서의 문장을 하나씩 확인했을 때 79.4%가 정확한 것으로 판정됐다. 제시한 발견 일곱 건 가운데 셋은 프리프린트나 미발표 원고에 있던 결과를 그 원고를 보지 않고 다시 찾아낸 것이고, 넷은 새로운 기여다.

심사를 통과한 사례도 있다. Intology의 발표에 따르면 Zochi가 작성한 논문 Tempest는 ACL 2025 본 학술대회 논문집에 채택됐다. 다만 그림 작성과 인용 형식, 사소한 수정은 사람이 했고, 제출 전의 결과·코드 검증과 심사자에게 보낸 답변도 사람이 맡았다.

Sakana AI의 첫 AI Scientist는 논문 한 편을 처음부터 끝까지 만드는 데 약 15달러가 든다고 보고했다. 생성한 논문 수로 전체 비용을 나눈 본문의 계산으로는 편당 10~15달러다. 후속 시스템인 AI Scientist-v2는 ICLR 2025 워크숍에 세 편을 제출했고, 그중 한 편은 평균 6.33점으로 워크숍 채택 기준을 넘었다. 전체 제출작 가운데 상위 약 45%에 드는 점수다. Sakana 연구진은 자체 검토에서 세 편 모두 ICLR 본 트랙 기준에 미달한다고 적었다. 기준을 넘은 원고는 사전 합의에 따라 메타 리뷰 전에 철회했다.

Kosmos 보고서의 문장 79.4%가 정확했다면 나머지 20.6%는 정확성을 따로 확인해야 한다. 6개월치로 평가된 작업이 짧은 시간에 나와도, 그 20.6%에 해당하는 문장을 찾는 일은 사람 몫이다. 그러려면 각 문장이 무엇을 보고 만들어졌는지가 기록으로 남아 있어야 한다.

완전 자동화에도 실행과 검증의 빈틈은 남는다

워크숍 심사를 통과한 뒤에도 실행과 검증의 문제는 남았다. AI Scientist-v2의 저자들은 정말 새롭고 파급력이 큰 가설을 세우고, 혁신적인 실험 방법을 설계하고, 설계 선택을 깊은 분야 지식으로 정당화하는 일이 완전 자동 시스템에 여전히 어렵다고 적었다. 자체 검토에서는 LSTM 기반 신경망을 Hochreiter와 Schmidhuber 대신 Goodfellow(2016)의 것으로 돌린 인용 오류도 찾았다. 첫 AI Scientist를 외부에서 평가한 연구가 보고한 한계는 앞의 연구들이 지적한 약점과 겹쳤다. 첫 AI Scientist는 키워드 검색에 기댄 문헌 검토로 새로움을 판정해 micro-batching 같은 이미 알려진 기법을 새것으로 분류했다. 제안한 실험 열두 건 가운데 다섯 건(42%)은 코드 오류로 돌지 못했고, 생성한 원고 일곱 편 가운데 네 편에는 틀리거나 지어낸 수치가 들어갔다.

과제를 통제해 측정하면 이 문제는 더 뚜렷해진다. ResearchGym은 ICML·ICLR·ACL 논문 5편을 바탕으로 제안 기법만 블라인드 처리하고 데이터와 베이스라인은 남긴 평가 환경을 만들었다. 39개 세부 과제에서 GPT-5의 완료율은 평균 26.5%였고, 전체 평가 15회 가운데 베이스라인을 넘은 것은 한 번뿐이었다. 그 한 번의 결과는 ICML 2025 Spotlight 해법의 수치를 앞섰다. 저자들은 주된 실패 원인으로 조급함, 시간·자원을 비효율적으로 쓰는 일, 약한 가설을 과신하는 일, 병렬 실험 조율의 어려움, 문맥 길이 제약을 들었다.

파일·명령·결과를 연구 기록으로 남긴다

실행의 일부를 모델과 도구에 맡기더라도, 연구자는 실행 조건을 정하고 결과를 검증할 책임을 맡는다. 그러려면 무엇을 보고 무엇을 실행했는지가 남아 있어야 한다.

요청을 자세히 설명하고, 잘못을 지적하고, 빠진 맥락을 보충하면 답이 나아질 때가 있다. 그러나 이 방식에서는 사용자가 매번 상황을 기억하고 같은 설명을 반복해야 한다. 작업이 길어질수록 이 반복이 쌓인다.

연구가 바로 그런 작업이다. 실험은 며칠씩 이어지고 원고는 여러 차례 바뀐다. 심사 의견에 답하려면 몇 달 전의 결과와 지금의 코드 상태를 함께 열어 봐야 한다. 이때는 프롬프트 대화보다 AI의 오류를 나중에 추적하고 다시 검증할 수 있도록 짠 작업 구조가 더 유용하다.

읽은 파일과 돌린 명령과 그 결과를 적어 둔다. 모두 그날 손에 있던 것이므로 새로 만들 필요가 없다. 이것만 있으면 모델이 바뀌거나 세션이 끊겨도 같은 자리에서 이어 갈 수 있다.

적어 둘 자리도 미리 정한다. 부록의 first-day-workspace-checklist.md에는 이 기록을 어디에 둘지 정하는 표가 있다. project goal, code truth, dataset truth, experiment truth, manuscript truth 줄마다 Primary source와 Secondary source를 적는 표다. 어느 자료를 기준으로 삼을지 미리 정해 두면, 나중에 요약과 파일이 어긋나도 정해 둔 쪽을 그대로 따르면 된다.

모델 성능에 따라 탐색 속도와 정리 품질은 달라진다. 어떤 모델을 쓰든 같은 파일과 로그를 보고 같은 절차를 따른다.

이 기록은 파일로 남고, 다음 연구를 시작할 때 사람과 에이전트가 함께 읽는다.

1부 검증 가능한 연구 기록

에러 로그를 붙여 넣으면 모델은 몇 초 안에 원인을 설명한다. 문장은 매끄럽고 수정안도 함께 나오니, 곧바로 고친 뒤 실험을 다시 돌리고 싶어진다.

그 설명이 맞는지는 파일을 열고 명령을 실제로 돌려 봐야 안다. 그래서 답을 실행에 옮기기 전에는 무엇을 확인했고 어떤 명령을 돌렸는지 남겨 둔다.

1장 AI와 사람이 나누어 맡을 일

AI는 넓게 찾아 후보를 추리는 일을 잘한다. 에러 로그를 주면 확인할 원인 후보를 내놓고, 파일·함수·config가 어디 있는지 짚고, 긴 로그와 심사 의견을 단계별로 나눈다. 반박문이나 README의 첫 문장을 제안하고, 여러 저장소와 실험 조건의 차이를 표로 정리하기도 한다.

AI가 하는 일은 후보를 좁히는 데서 끝난다. 실제 원인은 실험과 로그를 확인해야 정해지고, 후보 가운데 무엇부터 확인할지는 사람이 정한다.

목표와 범위는 사람이 정한다

Anthropic은 2025년 10월부터 2026년 4월까지의 Claude Code 세션 약 40만 개를 분석해 2026년 6월 보고서를 냈다. 이 보고서에서도 무엇을 할지 정하는 일과 어떻게 할지 고르는 일을 맡은 쪽이 달랐다.

무엇을 만들고 어디까지를 완료로 볼지 같은 계획 결정은 사용자가 약 70%를 내렸다. 어느 파일을 고치고 어떤 명령을 돌릴지 같은 실행 결정은 Claude가 약 80%를 내렸다.

보고서는 사용자의 숙련도를 다음 신호로 매겼다. 지시가 얼마나 정확한지, 무엇을 검증해 달라고 하는지, 사용자가 Claude를 바로잡는지 Claude가 사용자를 바로잡는지다. 숙련도는 사람마다 하나로 정하지 않고 과제마다 따로 매겼다.

이 가운데 무엇을 검증해 달라고 할지는 요청하는 사람이 직접 정한다. 실제 파일과 대조할 항목과 통과 기준을 정하는 일은 모델에 넘길 수 없다. 그래서 사람은 어디를 검증할지 짚는 데 힘을 쓴다.

어디를 검증할지 짚으려면 먼저 어느 dataset의 어느 split을 어떤 코드 경로와 metric으로 재는지 지목한다. 다음에는 실행할 때 실제로 읽힌 config를 확인한다. 마지막으로 AI가 낸 원인 후보를 단계별로 대조해 맞지 않는 것을 걷어 낸다.

여기서 단계란 데이터를 읽어 들이는 일부터 정합과 최적화를 거쳐 평가까지 이르는 구간이다. 어느 단계에서 틀어졌느냐에 따라 고칠 곳이 달라진다. 단계마다 이름을 붙이는 일은 2부에서 다룬다.

이 지목은 지난번에 무엇을 확인했는지 알아야 정확해진다.

보고서는 분석의 한계도 밝혔다. 세션에서 쓴 코드가 나중에 실제로 쓰였는지는 재지 못했고, 세션 분류는 모두 대화 기록을 읽은 모델이 했다. 뒤에서 기록마다 무엇까지 확인했는지 적어 두는 것도 같은 까닭이다.

자동화할수록 사후 검증이 중요해진다

답이 나올 때마다 화면을 지켜보는 방식으로는 오류를 잡기 어렵다. 자동화 연구는 오래전에 그 이유를 적어 두었다.

Bainbridge는 Ironies of Automation(1983)에서 공정 산업의 자동 제어를 중심으로 이 문제를 짚었다. 공장에 자동 장치를 들이는 이유는 그 장치가 사람보다 그 일을 잘하기 때문이다. 그러나 장치가 제대로 작동하는지 살피는 일은 다시 사람에게 남는다.

Bainbridge는 사람이 장치를 살피기 어려운 까닭도 설명했다. 판단을 규칙으로 다 적을 수 있다면 컴퓨터가 사람보다 빠르게, 더 많은 요인을 따져 그 판단을 내린다. 그러니 사람이 컴퓨터가 규칙을 제대로 따르는지 실시간으로 확인할 길은 없다.

사람에게는 계기판을 바라보는 일이 남는다. 변화가 드문 화면을 30분 넘게 높은 주의력으로 지켜보기는 어렵다. 수동 제어를 오래 쉬면 비상 상황에서 개입할 솜씨도 무뎌진다.

AI가 답을 만드는 동안 화면만 바라보는 사용자도 같은 처지다. 모델 안에서 무엇을 근거로 답을 만드는지 실시간으로 따라갈 방법이 없고, 화면을 오래 본다고 숨은 결함이 드러나지도 않는다.

그래서 답이 나온 뒤에 결과를 실제 상태와 대조한다. 대조할 기준은 미리 정해 둔다.

기준이 없으면 판단은 그때그때의 인상을 따라간다. Parasuraman과 Riley(1997)는 자동화를 지나치게 믿고 기대는 오용(misuse)과 믿지 못해 쓰지 않는 불용(disuse)을 나누어 분석했다.

어제 오탐이 한 번 났다고 도구를 접었다가 다음 주에 별 근거 없이 다시 꺼내 쓰는 일이 여기에 해당한다. 기록이 쌓여 있으면 며칠 동안의 인상 대신 지난번에 실제로 나온 결과를 보고 판단한다.

연구 기록에서 경계할 오류

원인은 실행 상태를 본 뒤에 정한다. 파일이 실제로 쓰였는지는 파일이 있다는 사실과 따로 확인한다.

경계해야 할 오류 왜 문제가 되는가
보지 않은 현재 상태 확정 파일명, memory, 요약만으로 최신 repo나 runtime을 단정한다
코드 존재와 실행 사용 혼동 저장소에 있는 모듈을 지금 돌아가는 방법으로 착각한다
숫자를 주장으로 넓혀 잡기 metric 하나를 방법 개선이나 generalization 주장으로 올린다
실패 단계 혼합 data loading, matching, optimization, evaluation 실패를 한 원인으로 합친다
위험 비용 무시 요청에 적지 않은 시간과 계산 자원, 심사자 신뢰, 원고 주장 범위가 판단에서 빠질 수 있다

원 파일, 실행 결과, 실행 조건을 나누어 남기면 이런 오류가 줄고, 추정이 확인한 사실처럼 읽히는 일도 막을 수 있다.

2장 대화 밖에 남겨야 할 기록

Thinking Machines의 Horace He는 2025년 9월 글에서 같은 프롬프트("Tell me about Richard Feynman")를 온도 0으로 1,000번 넣었다. 서로 다른 완성본이 80개 나왔고, 가장 자주 나온 완성본도 1,000번 가운데 78번이었다. 첫 102개 토큰은 1,000개가 모두 같았다. 103번째 토큰에서 992개는 Queens, New York을, 나머지 8개는 New York City를 골랐다.

출력이 달라진 원인은 서버의 배치(batch) 크기였다. 서버는 여러 요청을 묶어 한 번에 돌리고, 그 묶음의 크기는 그때그때 부하에 따라 달라진다. 커널은 묶음 크기에 따라 덧셈 순서를 바꾸므로 같은 입력에서도 다른 수가 나온다. 같은 묶음에 실린 다른 요청이 결과를 바꾼다.

같은 글에는 커널을 고친 결과도 있다. 묶음 크기와 상관없이 같은 순서로 더하는 커널로 바꾸자 1,000개가 모두 같아졌다. 따로 잰 속도 시험(Qwen3-8B로 요청 1,000개 처리)에서는 26초가 55초로 늘었고, attention 커널을 다듬어 42초까지 줄였다. 다듬은 뒤에도 기본 설정의 약 1.6배다.

재현성을 얻으려고 바꾼 곳은 추론 서버 안쪽의 커널이다. 외부 API 사용자는 이 커널에 손댈 수 없다.

모델이 낸 문자열은 그 자리에서 저장한다. 프롬프트만 적어 두었다가 나중에 다시 부르면 같은 답이 온다고 기대하지 않는다.

실행 상태는 대화 밖에서도 바뀐다

Suchman은 Plans and Situated Actions(1987)에서 계획이 행동을 세부까지 정한다는 가정을 비판했다. Suchman이 보기에 계획은 참고 자료이고, 실제 일은 그때그때 형편을 보며 해 나간다.

AI가 내놓는 설명과 수정안도 이런 뜻의 계획이다. 기록에는 그 자리에서 실제로 무슨 일이 있었는지를 남긴다.

Docker container, ROS2 topic, CUDA process, dataset split, calibration file, metric script, TeX table 같은 실행 상태는 대화 밖에서 바뀐다. 이런 변화는 누군가 확인해서 붙여 넣어야 대화창에 들어온다.

Hutchins는 Cognition in the Wild(1995)에서 현재 상태를 한 사람이 다 쥐고 있지 않다는 점을 보였다. 큰 군함이 항구에 들어갈 때 배의 현재 위치는 해도와 계기, 승조원들이 주고받는 절차가 함께 정한다.

배에서는 해도와 계기가 현재 상태를 계속 보여 준다. 연구실에서는 container나 dataset이 바뀐 사실을 누군가 확인해야 드러난다. 그래서 사람과 AI가 나중에 다시 열어 볼 상태는 파일에 남긴다.

AI의 설명과 확인한 사실을 나누어 적는다

받은 답 아래에는 먼저 모델의 설명을 요약하지 않고 그대로 옮긴다.

요약하면 그 순간 내 문장이 되어, 나중에는 어디까지가 모델의 말이었는지 알 수 없다. 옮긴 설명 아래에는 실제로 연 파일과 돌린 명령을 적고, 명령이 낸 결과를 붙여 넣는다.

끝에는 붙여 넣은 결과로 말할 수 있는 범위를 적는다. 이 칸이 가장 어렵다. 앞의 40만 세션 분석도 결론 옆에 재지 못한 것을 적어 두었다. 여기서도 결과에서 직접 확인되는 선까지만 적는다.

모델이 쓴 문장과 눈으로 본 사실을 섞어 적으면 같은 실수가 되풀이된다. 그럴듯한 가설이 확인된 원인처럼 읽히고, 저장소에 남아 있기만 한 코드가 실제로 돌아가는 코드처럼 원고에 들어간다. 조건이 다른 수치가 일반 성능으로 부풀고, 필요한 실험은 건너뛴 채 반박문 문장만 다듬게 된다. 인계 메모나 memory 파일이 원자료처럼 쓰이기도 한다.

모델의 말과 눈으로 본 것을 다른 줄에 적는다. 모델의 설명은 요약하지 말고 그대로 옮기고, 그 아래에 실제로 연 파일과 돌린 명령과 나온 결과를 적는다. 그래야 한참 뒤에 열어 봐도 어디까지가 모델의 말이고 어디부터가 확인한 사실인지 구별된다.

다시 열어 보려면 이 기록이 파일로 있어야 한다. 이 파일을 모델에게 쓰게 할 수도 있다. Anthropic의 맥락 관리 cookbook은 이때 쓰는 도구로 memory_20250818을 소개한다. 이 도구를 써도 파일을 실제로 만지는 쪽은 모델이 아니다.

Claude가 파일을 열거나 고치겠다고 요청하면, 그 요청을 받아 실행하는 것은 우리 쪽에서 돌리는 코드다. 요청할 수 있는 명령은 view·create·str_replace·insert·delete·rename이고, 이 명령이 닿는 곳은 우리 디스크다.

그래서 모델이 쓴 기록도 우리가 쓴 기록과 같은 파일 시스템에 놓이고, 언제든 열어 볼 수 있다. 이 파일은 맥락 창 밖에 있으므로 세션이 바뀌어도 남는다.

지난 기록은 현재 상태가 아니다

기록에 남는 것은 적을 때의 상태다. 며칠 뒤 열어 보면 경로도 명령도 그때 나온 숫자도 적어 둔 그대로지만, 그사이 기계 쪽 상태는 바뀌었을 수 있다.

ROS2에서는 보내는 쪽(publisher)과 받는 쪽(subscription)마다 QoS profile을 정한다. 그 가운데 reliability 설정은 메시지를 반드시 전달할지, 놓쳐도 넘어갈지를 정한다. 보내는 쪽과 받는 쪽의 설정이 맞아야 메시지가 건너간다.

ROS2 publisher와 subscription의 기본 reliability는 전달을 보장하는 RELIABLE이다. ROS2가 센서 데이터용으로 미리 정해 둔 profile은 일부를 잃더라도 최신 값을 빨리 받도록 BEST_EFFORT를 쓰고, 카메라나 LiDAR 드라이버가 이 profile로 보내기도 한다. 보내는 쪽이 BEST_EFFORT인데 받는 쪽이 RELIABLE이면 메시지가 오지 않는다.

지난주에 토픽이 들어오는 것을 보고 설정이 맞다고 적어 두었어도, 그사이 누가 받는 쪽을 기본값으로 돌려놓았다면 그 줄은 이제 틀렸다. 기록만 읽어서는 틀린 줄인지 알 수 없다. 그래서 적어 둔 파일을 열고 적어 둔 명령을 그대로 다시 돌린다.

답마다 붙이는 기록과 별도로, 작업 공간 전체의 상태를 적는 메모를 하나 둔다. 여기에는 프로젝트의 목표가 무엇인지, 지금 기준으로 삼는 코드 경로가 어디인지, 어느 dataset과 split을 쓰고 있는지, 실험과 원고가 어디까지 왔는지, 심사에서 걸릴 만한 곳이 어디인지를 적는다.

메모 끝에는 다음 작업에도 적용할 교정 사항을 적는다. 같은 것을 두 번 바로잡았다면 여기에 올려, 다음에 이 파일을 여는 사람이 알고 시작하게 한다. 부록 B의 빠른 시작 문서에 이런 메모를 채운 예가 있다.

메모를 어디에 둘지도 정한다. 채우다 보면 심사 의견 원문과 미공개 숫자가 들어오는데, 이런 줄은 공개 저장소에 두면 안 된다.

반복되는 실패 유형, 운영 규칙, 공개용 template은 공개 저장소에 둔다. 개인 대화 원문, 개인 경로, 심사 의견 원문, 미공개 숫자, 인증 정보는 로컬 기록에 남긴다. 부록 D도 작업을 다시 시작할 때 이 경계를 확인하게 한다.

메모는 지난번에 보고 적은 값이다. 지금도 그런지는 돌려 봐야 안다.

메모를 읽고 끝내지 않는다. 메모에 적힌 명령을 그대로 다시 돌려 현재 상태와 대조한다. 코드가 그대로여도 container나 split이 바뀌었으면 같은 조건이 아니다.

돌려 봐야 아는 현재 상태는 여러 곳에 흩어져 있다. 저장소에서는 branch·commit과 수정된 파일 내역을 살핀다. 실행 환경에서는 동작 중인 process·container·device 상태를 점검한다. 데이터에서는 dataset의 version과 split과 calibration을, 지표에서는 metric 출력과 plot과 실패한 실행을 확인한다. 원고에서는 TeX diff와 figure 원본과 table을 연다. 마지막으로 project memory와 인계 메모에서 지난 작업의 방향을 찾는다.

project memory와 인계 메모는 지난 작업의 맥락을 적은 글이다. 나머지는 지금 직접 열거나 다시 돌려서 확인할 대상이다. 메모를 누가 썼든, 한 곳을 확인했다고 다른 곳의 상태까지 확인되지는 않는다. 저장소가 깨끗해도 container는 그때 그대로인지 따로 봐야 한다. metric 출력이 남아 있어도 지금 코드에서 나온 값인지는 데이터 쪽까지 열어 봐야 안다.

실행 쪽을 여는 방법은 부록 F의 로봇 실험 문제 해결 안내서에 모아 두었다. 환경을 갈아엎기 전에 pip show와 dpkg -l | grep과 apt policy로 지금 무엇이 깔려 있는지 적는다.

새 terminal에서 package가 안 보이면 echo $AMENT_PREFIX_PATH로 지금 잡힌 workspace를 확인한다. 토픽이 안 들어올 때 ros2 topic list와 ros2 node list를 함께 찍으면 노드가 안 뜬 것인지 이름이 다르게 붙은 것인지 가려지고, 그 결과가 명령 출력으로 남는다.

모델이 읽어 둔 정보도 같은 식으로 낡는다. 우리가 파일을 열고 명령을 돌리면 그 결과가 모델의 맥락 창에 그대로 쌓이기 때문이다.

앞의 cookbook은 맥락 관리를 전혀 하지 않은 실행에서 창을 무엇이 채우는지 쟀다. 창은 335,279 토큰까지 찼고, 그중 96.3%가 읽어 들인 파일 내용이었다. 도구 호출 기록은 1.9%, 모델이 쓴 추론 문장은 1.7%였다.

창에 든 것은 거의 다 어느 시점에 읽은 파일의 사본이다. 그 파일이 나중에 바뀌면 모델은 옛 내용을 들고 답한다. 우리 메모가 낡는 이유와 같다. 창 안에는 낡았다는 표시도 없다.

그래서 다시 읽을 자료는 창 밖에 둔다. 같은 cookbook은 세션을 두 번 이어 돌려 차이를 쟀다. 첫 세션이 문서 네 개를 읽고 memory 파일에 정리해 둔 경우, 둘째 세션은 그 파일을 읽은 뒤 남은 문서 네 개만 읽었고 창은 172,623 토큰까지 찼다. memory 디렉터리가 빈 조건에서는 문서 여덟 개를 모두 다시 읽어 333,977 토큰까지 찼다.

여기서 창 밖은 앞에서 본 우리 디스크다.

긴 작업은 단계마다 기록을 남긴다

긴 작업을 한 세션에 맡기기 어렵다는 것은 과제 길이를 바꿔 가며 잰 결과에서도 보인다. METR은 과제마다 숙련자가 끝내는 데 걸리는 시간을 매겨 두고, 모델이 절반의 확률로 끝내는 과제 길이를 그 모델의 time horizon으로 잰다. 2026년 1월 발표에서 가장 긴 값은 Claude Opus 4.5의 320분이었다. 숙련자가 320분 걸리는 과제를 이 모델이 절반의 확률로 끝낸다는 뜻이다.

이 값은 빠르게 오른다. 두 배가 되는 데 걸린 기간은 전체 구간에서 196.5일, 2023년 이후로 좁히면 130.8일, 2024년 이후로 좁히면 88.6일이었다. 측정의 한계도 있다. 8시간 넘는 과제 31개 가운데 사람이 실제로 걸린 시간을 잰 것은 5개뿐이고 나머지는 추정치이며, 신뢰구간도 아직 넓다.

과제가 길수록 성공률이 떨어지는 모양을 단순한 모형으로 설명한 Toby Ord(2025)의 연구도 있다. 사람 기준으로 1분이 늘 때마다 일정한 확률로 실패한다고 놓으면, 이 모형이 Kwa 등(2025)이 모은 연구 공학 과제에서 관측된 곡선에 대체로 들어맞는다. 이렇게 놓으면 성공률은 과제 길이에 따라 지수 함수 꼴로 떨어지고, 길이가 두 배가 되면 성공률은 제곱이 된다. Ord는 긴 과제일수록 하위 단계가 많고 그중 하나만 어긋나도 전체가 실패하기 때문에 이 모형이 맞는 것일 수 있다고 보았다.

공개 모델 10종으로 에피소드 23,392건을 돌린 연구에서 pass@1 평균은 짧은 과제 76.3%에서 아주 긴 과제 52.1%로 내려갔다. 긴 과제의 결과 분산이 짧은 과제의 두 배를 넘은 모델은 성적이 가장 좋은 네 개였고, 성적이 낮은 모델은 길이와 상관없이 고르게 실패했다.

창에 남은 정보를 모델이 실제로 쓰는지 잰 보고서도 있다. Chroma의 2025년 보고서 Context Rot은 GPT-4.1, Claude 4, Gemini 2.5, Qwen3를 포함한 모델 18종에 입력 길이만 늘려 가며 과제를 주었다. 간단한 과제에서도 입력이 길어질수록 성능이 점점 불안정해졌다.

필요 없는 맥락을 제때 비우면 성능이 오르기도 한다. Anthropic의 내부 평가에서 agentic search 성능은 맥락 편집(context editing)만 쓴 경우 기준보다 29%, memory 도구까지 함께 쓴 경우 39% 올랐다. 따로 돌린 100턴 웹 검색 평가에서는 맥락 편집으로 토큰 소비가 84% 줄었다. 평가 조건이 서로 다르므로 각 수치는 제 조건과 함께 읽는다.

긴 작업을 한 세션에 밀어 넣지 않는다. 사람 기준으로 몇 시간을 넘길 일은 단계마다 기록을 남기며 끊어 간다. 창에 정보가 남아 있어도 모델이 그것을 쓴다는 보장은 없다.

연구 작업은 며칠에서 몇 달씩 걸리므로 320분을 넘기는 일이 많다. 그런 일은 단계마다 기록을 파일로 남기고, 다음 세션에서 그 기록을 읽어 이어 간다.

모델이 쓴 요약은 원자료가 아니다

지금까지 다룬 기록에는 확인한 파일과 명령 결과가 함께 들어 있다. 작업 공간에는 모델이 줄여 쓴 글도 쌓인다. 대화가 길어지면 생기는 압축본, 다음 세션에 넘기려고 써 둔 인계 메모, project memory에 적힌 몇 줄이다. 이런 글은 확인 기록보다 가볍게 다룬다.

압축본은 compaction이 만든다. 창에 든 토큰이 개발자가 정해 둔 수를 넘으면 서버가 자동으로 압축을 건다. 앞의 cookbook에 따르면 압축은 대화 전체에 걸린다. 사용자가 한 말, 모델이 한 말, 도구 호출, 도구 결과, 앞서 만든 압축본까지 요약 하나로 합쳐진다.

합쳐진 내용은 요약에서 되살릴 수 없다. cookbook의 실행에서는 압축 한 번이 18만 토큰 기준을 넘긴 앞 대화를 약 2,783 토큰짜리 요약으로 바꿨다. 요약에 빠진 내용은 원래 대화가 남아 있어야 되찾는다.

같은 cookbook은 clearing이라는 다른 방식도 소개한다. clearing은 다시 불러올 수 있는 지난 도구 결과를 창에서 지우고, 그 호출을 했다는 기록은 남긴다. 호출 기록이 있으면 결과를 다시 받아 볼 수 있다. 다만 명령이 같다고 출력이 같다는 보장은 없다. 입력 파일과 실행 환경이 바뀌거나 외부 서비스가 갱신될 수 있으니, 필요한 결과와 당시 조건은 앞에서 말한 대로 명령과 따로 적어 둔다.

compaction은 원래 대화를 요약으로 바꾸므로, 그 뒤의 요약은 원문과 대조할 수 없다. clearing과 memory를 함께 쓸 때는 exclude_tools에 memory를 넣어 memory 도구의 결과는 지우지 않게 한다.

인계 메모와 project memory도 compaction을 거치지 않았을 뿐 모델이 줄여 쓴 글이다. 어느 대목이 어디서 왔는지 가리려면 원문을 옆에 놓는다.

요약을 확인하려면 원문이 있어야 한다는 것을 보인 연구가 있다. Maynez 등은 뉴스 기사와 요약문을 나란히 놓고 판정자들에게 기사가 뒷받침하지 않는 구간을 표시하게 했다. 판정자들은 기사를 옆에 두고 읽었다.

기사가 뒷받침하지 않는 내용이 들어간 요약문은 모델마다 70%를 넘었다. 2020년 무렵의 요약 모델 네 종이 뉴스를 한 문장으로 요약한 결과에서 나온 값이다.

메모만 읽어서 걸러지는 것은 앞뒤가 맞지 않는 문장뿐이다. 사실과 어긋난 문장도 앞뒤는 맞게 읽힌다. "calibration을 다시 맞춘 뒤 성능이 올랐다"는 줄에는 이상한 데가 없다. 언제 무엇을 만졌는지 적혀 있지 않으니, 그 줄만으로는 참인지 거짓인지 가릴 수 없다.

Ji 등의 환각 조사는 원문만으로는 참인지 거짓인지 확인할 수 없는 내용이 들어간 출력을 extrinsic hallucination이라 부른다. 같은 조사는 이런 출력이 읽는 사람에게 왜 걸리지 않는지도 적었다.

Hallucinated text gives the impression of being fluent and natural despite being unfaithful and nonsensical.

요약을 원자료로 쓰지 않는다. 인계 메모나 압축본을 읽을 때는 옆에 원문 파일을 놓고 줄마다 맞춘다. 앞뒤가 맞는 채로 틀린 문장은 메모만 읽어서는 안 걸린다.

문장의 겉모습으로는 참과 거짓이 갈리지 않으니, 무엇을 근거로 삼을지를 세션 첫머리에 정해 둔다. 부록 B에는 상태 메모와 함께 첫 세션에 넣을 프롬프트가 있고, 거기에 이 줄이 들어 있다.

Do not infer project truth from summaries when source files or artifacts are
available.

작업을 다시 시작하면 현재 상태부터 확인한다

원칙은 옆에 파일을 놓고 맞춰 보는 것이다. 그런데 며칠 만에 자리에 앉으면 파일보다 요약을 먼저 읽게 된다. 자리를 비운 사이 기계가 무엇을 했는지는 돌아와서 남은 글을 읽어야 알 수 있기 때문이다.

이때 요약만 읽는 사람은 자동 장치를 지켜보기만 한 사람과 같은 처지에 놓인다.

Endsley는 상황 인식을 세 단계로 나누었다. 지금 무엇이 있는지 알아채는 단계, 그것이 무슨 뜻인지 이해하는 단계, 앞으로 어떻게 될지 내다보는 단계다.

Endsley와 Kiris는 1995년 내비게이션 실험에서 자동화 수준을 사람이 직접 판단하는 조건부터 완전 자동화까지 다섯 단계로 나누어 상황 인식을 비교했다. 완전 자동화 조건의 참가자들은 정보를 알아채는 수준은 유지했지만 상황의 뜻을 이해하는 수준은 수동 조건보다 유의하게 낮았다. 실험은 앞의 두 단계만 쟀으므로 예측 단계는 이 실험으로 알 수 없다.

Endsley는 이 실험을 다시 정리한 글에서 지켜보는 사람의 처지를 이렇게 적었다.

When acting as monitor of an automated system, people are frequently slow in detecting that a problem has occurred necessitating their intervention.

자동 장치를 지켜보는 사람은 개입이 필요한 문제가 생겼다는 사실을 자주 늦게 알아챈다는 말이다. 알아챈 다음에도 일이 남는다.

Once detected, additional time is also needed to determine the state of the system and sufficiently understand what is happening in order to be able to act.

알아챈 뒤에도 지금 상태가 어떤지 파악하고 무슨 일인지 충분히 이해해야 손을 댈 수 있는데, 거기에 시간이 또 든다는 말이다.

이 실험 결과를 연구실 작업에 그대로 옮길 수는 없다. 요약을 읽고 "여기까지 했지"라고 떠올리는 일도 무엇이 남아 있는지 알아채는 데서 시작한다는 점만 가져온다. 어디에 무엇이 있었는지는 요약으로 찾는다. 그것이 지금도 같은 상태인지는 명령을 돌려 봐야 안다.

3장 점수와 판정의 근거를 확인한다

한 번 잰 수치와 자동 채점기의 판정은 따로 검증한다. 실행값은 여러 번 재서 흔들리는 범위를 확인한다. 채점기 판정은 일부를 뽑아 원자료와 대조한다. 도구 호출 벤치마크 네 종의 과제 496개를 전문가가 다시 판정한 감사에서는 채점기 판정과 사람 판정이 92건(18.5%) 달랐다. 상태 비교가 지나치게 엄격해 맞게 수행한 과제를 실패로 본 경우, 정답 자체가 틀린 경우, 바뀌지 않은 상태를 성공으로 본 경우가 있었다.

점수는 반복 횟수와 함께 적는다. 한 번 돌린 값만으로 비교를 확정하지 않는다. 비용이 허락하면 같은 조건에서 3회 이상 돌려 최솟값과 최댓값까지 함께 남긴다.

반복 횟수와 불확실성을 함께 적는 관행은 아직 드물다. 기계학습·자연어처리 학회 여섯 곳의 논문 46,114편에서 LLM 벤치마크 논문 445편을 추린 조사에서, 결과를 비교할 때 불확실성 추정이나 통계 검정을 쓴 논문은 16%였다.

널리 쓰이는 LLM 벤치마크 60종을 분석한 연구에서는 29종이 포화 정도가 높거나 매우 높았다. 상위 모델들의 점수가 몰려 통계적으로 구별되지 않는 상태다.

벤치마크 점수도 채점기 오류와 포화의 영향을 받는다. 그래서 점수에는 반복 횟수와 실행 조건을 함께 적는다. 한 번 돌린 수만 보고 다음 결정을 내리면 그 결정도 그 수만큼 흔들린다.

확인 근거는 자기 평가 바깥에서 찾는다

모델에게 자기가 낸 답을 다시 채점하게 해도 실제 파일이나 실행 결과가 새로 생기지는 않는다. 판정 문장이 하나 더 붙을 뿐, 답을 확인할 근거는 그대로다.

그래서 모델에게는 무엇을 보았고 무엇을 실행했는지 적게 한다. 맞는지는 사람이 파일을 열어 판단한다.

근거에 따라 말할 수 있는 범위가 달라진다

명령이 낸 결과를 바탕으로 어디까지 말할 수 있는지는 무엇을 함께 확인했는지에 따라 달라진다.

자료 예 말할 수 있는 범위
원 파일 소스 코드, config, TeX, CSV, log 파일 안에서 직접 확인한 내용
실행 결과 command output, generated figure, metric result 해당 실행에서 나온 결과
조건을 확인한 결과 dataset, split, metric, baseline을 확인한 숫자 같은 조건 안의 비교
요약 handoff, compact summary, memory note 다음에 확인할 위치
AI 추정 원인 추정, 구조 해석, 요약 판단 확인해야 할 설명

원 파일로는 파일 안에 적힌 것을 확인한다. 코드가 실행됐다는 사실은 실행 결과로 확인한다.

실행 결과는 그 실행에서 실제로 나온 값이므로, 그 실행이 일어났다는 사실까지 말할 수 있다. 다른 실행과 비교하려면 결과 파일에 조건도 함께 기록되어 있어야 한다.

조건까지 확인하면 그 결과를 비교할 수 있다. dataset과 split과 metric과 baseline을 대조했으므로 같은 조건 안에서는 두 수치를 나란히 놓는다. 조건이 다른 수치를 비교하려면 조건을 다시 대조한다.

요약은 모델이 줄여 쓴 글이다. 그 안의 어느 대목이 참인지 가리려면 원자료를 연다. 요약은 어느 원본을 열지 찾는 색인으로 쓴다.

AI 추정으로는 내용을 확정하지 않는다. 어떤 파일이나 실행 결과에 기댄 설명인지 드러나지 않으면 확인할 거리로만 쓴다.

앞에서 말한 기록의 각 줄도 이 표에 맞춰 볼 수 있다. 모델이 만든 설명은 AI 추정, 실제로 연 파일은 원 파일, 돌린 명령과 나온 결과는 실행 결과에 해당한다. 줄마다 그 자료로 말할 수 있는 범위를 적는다.

가령 final_results.csv를 열어 숫자를 확인했다면, 우선 그 파일 안의 내용을 읽었다고 말할 수 있다. 그 숫자를 만든 명령과 config까지 찾으면 해당 실행에서 나온 결과인지 확인할 수 있다. 다른 결과와 비교하려면 dataset과 split과 metric과 baseline도 대조해야 한다.

같은 실험 숫자를 다시 볼 때 먼저 물을 내용은 정해져 있다. 어느 dataset의 어느 split인지, 그 지표는 값이 큰 쪽이 좋은지 작은 쪽이 좋은지, 어느 metric script와 어느 baseline인지, 실제로 읽은 출력이 무엇인지다.

이 항목을 채우면 그 숫자가 어느 조건에서 나온 값인지 정해지고, 같은 조건의 baseline과 비교할 수 있다. final_results라는 이름에는 이 가운데 어느 조건도 들어 있지 않다.

4장 연구를 다시 시작할 때

작업을 다시 시작할 때는 무엇부터 열지 순서를 미리 정해 둔다. 순서가 없으면 손에 잡히는 요약부터 읽게 되고, 요약의 오류는 읽는 동안 묻힌다.

  1. 현재 repo와 공개/비공개 경계를 확인한다.
  2. project memory나 handoff 문서로 진행 방향을 파악한다.
  3. 관련 소스와 설정 원본 파일을 연다.
  4. 실행 결과가 필요하면 command와 output path를 대조한다.
  5. 원고 작업이면 table, figure, paragraph가 서로 맞는지 확인한다.
  6. summary와 원본 파일이 다르면 원본 파일을 따른다.
  7. 다음에 할 구체적인 행동 하나를 정한다.

경계부터 확인하는 까닭은 뒤에 하는 일이 모두 무언가를 적는 일이기 때문이다. 지금 연 저장소가 공개 저장소인지 로컬 기록인지 먼저 알아야 심사 의견 원문이나 미공개 수치가 공개 저장소에 들어가지 않는다.

1단계부터 3단계까지는 근거 자료를 찾아 연다. 4단계부터는 명령과 실행 결과를 검증한다. 요약은 3단계까지 무엇을 열지 찾는 데만 쓴다.

그래서 작업을 시작할 때는 요약 전체를 넣지 않고 먼저 열어 볼 이름만 넘긴다. Anthropic은 경로·질의·링크 같은 가벼운 식별자만 들고 있다가 필요할 때 불러오는 방식을 just in time 전략이라 부르고, 자료를 미리 처리해 넣어 두는 방식과 구분했다. 미리 넣는 자료가 많을수록 창 안의 토큰이 늘고, 토큰이 늘면 앞에서 본 context rot(입력이 길어질수록 성능이 떨어지는 현상)이 생긴다.

3단계와 4단계에서는 파일과 실행 조건이 서로 맞는지 확인한다. 코드가 같아도 split이 바뀌었으면 같은 조건이 아니다. 원본 파일을 볼 때는 config, split, calibration file을 함께 열어 대조하고, 명령과 출력 경로를 볼 때는 실행 당시의 container와 환경 변수도 확인한다.

원고 작업에서는 5단계에서 문단에 인용한 수치가 방금 확인한 실행 결과에서 나온 값인지 대조한다. 그러려면 TeX diff, figure 원본, table을 함께 연다.

열어 본 원 파일이 요약과 다르면 6단계로 간다. 기존 요약은 고치지 않고, 어긋난 지점과 지금 확인한 값을 새 기록에 남긴다. 그래야 다음에 무엇이 어긋났는지 비교할 자료가 남는다. 같은 항목이 두 번 어긋나면 상태 메모의 교정 사항으로 올린다.

한 번에 하나만 바꾼다. branch, config, script, 원고 문단을 한꺼번에 손대지 않는다. 하나만 바꿔 두면 수치가 달라졌을 때 확인할 변경점이 하나뿐이다. 그래도 반복 실행의 변동과 환경 변화는 따로 확인한다.

다음 행동 하나를 정하고 거기서 멈출 때도 있다. 답이 계속 나와도 근거가 더 늘지 않으면 멈춘다. 부록 D가 꼽는 경우는 같은 단계에서 근거가 그대로일 때, 도구 실패와 방법 실패가 섞였을 때, 실험 조건이 바뀌었는데 숫자를 비교하려 할 때, 심사 위험이 남았는데 문장만 다듬고 있을 때, 비공개 자료가 공개 문서에 섞일 위험이 있을 때다. 이런 때에도 AI는 계속 답한다. 멈출지는 사람이 정한다.

멈추든 계속하든 그날 한 일은 기록에 남긴다. 다음에 앉는 사람이 그 기록을 보고 어디부터 열지 정한다.

실행 전에 작업 범위와 근거를 정한다

이어 가는 작업에서는 요청 하나가 쉽게 커진다. 로그 분석으로 시작한 일이 코드 수정으로 번지고, 실험 해석과 원고 문장까지 딸려 오기도 한다.

요청이 번지면 여러 곳이 함께 바뀌고, 결과가 달라졌을 때 원인 후보도 그만큼 늘어난다. 기록해 둔 작업을 다시 돌릴 때 그사이 바뀐 곳이 하나라면 그 변경의 영향부터 확인한다. 그것이 결과 차이의 원인인지 확정하려면 다른 조건과 반복 실행의 변동도 대조한다.

요청은 실행되는 도중에 번진다. 실행 도중 언제 도구를 부를지 정하는 방법은 연구에서 먼저 나왔다.

ReAct는 모델이 생각을 한 줄 적고 행동을 한 번 하는 일을 번갈아 하게 했다. 행동으로 지식 베이스나 환경에서 새 정보를 얻고, 그 정보로 계획을 고친다. Toolformer는 계산기, 질의응답, 검색, 번역, 달력 API를 언제 부르고 어떤 값을 넘길지 모델이 스스로 정하도록 학습시켰다.

두 연구에서 모델은 스스로 도구를 부르고 그 결과를 다음 판단에 썼다. 연구실에서는 연구자가 그 도구 출력을 나중에 다시 보고, 원고 문장의 근거로 쓰거나 심사 의견에 답할 때 인용한다.

도구 출력은 모델의 설명과 섞여 작업 기록에 들어온다. 그래서 도구를 불렀다는 사실과 그 출력으로 어디까지 말할 수 있는지를 나누어 본다. git diff, ros2 출력, metric CSV, PDF 빌드 결과마다 각각 무엇까지 근거로 삼을 수 있는지 짚어 둔다.

도구를 부르는 일을 여러 에이전트에 나눌 수도 있다. Anthropic의 multi-agent research system은 lead agent 하나가 일을 나누고 subagent 여럿이 나눠 받은 일을 병렬로 하는 구조를 설명한다.

Anthropic의 내부 research 평가에서 Opus 4가 lead를 맡고 Sonnet 4 여럿이 subagent로 붙은 구성은 Opus 4 하나만 쓴 구성보다 90.2% 높은 점수를 받았다. 문서는 S&P 500 정보기술 업종 기업의 이사진을 모두 찾는 과제를 예로 들었다.

lead agent가 subagent를 병렬로 띄우고 subagent도 도구를 병렬로 부르게 바꾸자, 복잡한 질의에 걸리는 시간이 최대 90% 줄었다.

문서는 비용도 밝혔다. 에이전트는 일반 대화보다 토큰을 약 4배, 여러 에이전트를 쓰는 시스템은 약 15배 쓴다. BrowseComp 성능 차이를 분석한 대목에는 token usage by itself explains 80% of the variance라고 썼다. 성능 분산의 80%를 토큰 사용량 하나로 설명할 수 있었다는 뜻이다.

여러 에이전트에 맞지 않는 일도 문서에 적혀 있다. 모든 에이전트가 같은 맥락을 공유해야 하거나 에이전트 사이에 의존이 많은 일이다. 문서는 대부분의 코딩 작업이 research보다 병렬로 나눌 부분이 적고, LLM 에이전트가 실시간으로 일을 나누고 조율하는 데에도 아직 서툴다고 적었다.

연구실에서 코드를 고치고 그 결과를 실험 해석과 원고 문장으로 잇는 일은 맥락을 많이 공유하고 단계끼리 의존도 높다. 같은 dataset과 config를 계속 함께 봐야 하고, 뒤 단계의 판단이 앞 단계 출력의 세부에 달려 있기 때문이다.

에이전트를 하나만 두어도 돌아온 결과는 사람이 확인한다. 앞에서 본 자동화의 역설이 여기에도 해당한다.

확인할 곳을 하나로 줄이려면 AI 작업 한 번이 바꿀 수 있는 범위를 좁게 정한다.

기록은 답을 받은 뒤에 남기지만, 바꿔도 되는 범위는 답을 보기 전에 정한다. 매끄러운 답을 받으면 거기서 제안한 수정까지 따라가기 쉽고, 그러면 작업 범위를 모델의 제안이 정하게 된다.

그래서 요청을 보내기 전에 부록의 experiment-contract.md를 연다. 이 양식에는 실험 조건과 명령을 적는 칸이 있고, 그 가운데 핵심은 Evidence Gate 칸이다. 이 실행으로 말해도 되는 것, 말하면 안 되는 것, 그 선을 넘으려면 무엇이 더 필요한지를 세 줄로 적는다.

이 세 줄은 실행 전에 쓴다. 결과를 본 뒤에 쓰면 나온 수치에 맞춰 기준을 바꾸게 되고, 좋은 값이 나오면 주장을 넓히고 싶어진다.

연구 작업의 종류부터 정한다

무엇을 바꿀지는 지금 하는 일이 어떤 종류인지에 따라 달라지고, 종류마다 근거로 삼는 것도 다르다. 구현 디버깅에서는 실행 출력이, 원고 주장을 고칠 때는 실험 조건이 근거다. 둘을 한 요청에 섞으면 무엇을 근거로 무엇을 정했는지 흐려진다.

증상이 어느 단계에서 생겼는지도 먼저 가른다. 부록의 stage-local-debugging.md는 단계마다 범위에 넣을지 묻고, 넣었다면 근거를 옆 칸에 쓰게 한다. 근거 칸이 빈 단계는 아직 짐작이다. 단계를 짐작으로 고치면, 고친 뒤에도 그것이 원인이었는지는 짐작으로 남는다.

연구 작업은 대략 다음과 같이 나뉜다. 이전 세션을 이어받는 작업은 상태 복원이다. 코드·Docker·ROS2 이슈 해결은 구현 디버깅이다. 새 실험 조건을 정하는 일은 실험 설계다. 나온 수치와 표를 분석하는 일은 결과 해석이다. 논문에서는 실험을 주장에 연결하거나, 원고 주장의 근거를 고치거나, 심사 의견에 답한다. 새로움과 비교 위치를 정하는 일은 관련 연구 정리에 속한다. 지금 하는 일에 여러 이름이 겹쳐 붙으면 요청이 번졌다는 신호다.

에이전트의 실행 권한을 먼저 정한다

작업 종류를 정한 다음에는 AI가 어디까지 해도 되는지 정한다. 읽기와 실행 사이에 선을 그어 두어야 요청한 일과 실제로 일어난 일이 맞는다. 파일만 보라고 했는데 파일을 고쳐 돌아오면 무엇이 바뀌었는지 다시 추적해야 한다.

권한은 대략 다음 단계로 나뉘고, 뒤로 갈수록 되돌리기 어렵다. 읽기와 분석만 맡기거나 구조와 계획만 제안받는 단계에서는 파일이 그대로다. 명령 실행을 허용하되 파일 수정은 따로 확인하는 단계부터 상태가 달라질 수 있다. 명령은 프로세스, 캐시, 결과 디렉터리를 남기기 때문이다. 수정까지 맡기면 저장소가 바뀐다. 실행과 결과 확인까지 요구하면 그 결과가 다음 판단의 근거가 된다.

권한을 고를 때는 어긋났을 때 되돌릴 수 있는지를 기준으로 삼는다. 파일을 읽기만 하면 되는 일이면 읽기만 요청하고, 실행 결과가 있어야 다음 판단을 할 수 있으면 실행을 요청한다.

적어 둔 권한은 사람이 지키지만, 기계에 조건을 걸어 지키게 할 수도 있다. Claude Code의 hook은 정해진 시점에 셸 명령, HTTP 요청, 모델 프롬프트 같은 처리를 걸어 두는 기능이다.

hook을 거는 시점은 실행 주기에 따라 나뉜다. 세션마다 한 번 실행되는 것(SessionStart·SessionEnd), 요청마다 한 번 실행되는 것(UserPromptSubmit·Stop), 도구를 부를 때마다 실행되는 것(PreToolUse·PostToolUse)이 있다.

PreToolUse에 걸어 둔 명령이 종료 코드 2를 내면 그 도구 호출은 막힌다. 무엇을 막을지는 거기에 연결한 스크립트가 정한다.

이번 작업을 읽기만으로 정했다면 편집 도구가 불릴 때 종료 코드 2가 나오게 해 둔다. 그러면 호출이 그 자리에서 멈추고, stderr에 쓴 내용이 막은 이유로 Claude에게 전해진다. 종료 코드 대신 JSON으로 hookSpecificOutput에 "permissionDecision": "deny"를 내보내도 호출이 막히며, 이때는 permissionDecisionReason에 적은 내용이 막은 이유가 된다.

완료 보고에는 다시 확인할 근거를 남긴다

막은 이유든 실행 결과든 작업이 끝나면 파일에 흔적이 남는다. 앞의 Claude Code 사용 분석은 성공을 두 기준으로 셌다.

하나는 모델이 대화를 읽고 성공이라고 판단한 경우다. 다른 하나는 여기에 더해 확인할 수 있는 흔적이 남은 경우로, 작업에 맞는 commit이나 pull request, 통과한 테스트, 사용자가 분명히 밝힌 확인 같은 신호가 하나 이상 있어야 했다.

완료 보고에도 같은 기준을 쓴다. 나중에 보고서를 다시 읽을 때 작업을 확인할 수 있도록 실제 파일과 돌린 명령을 함께 남긴다.

에이전트를 여러 개 둘 때도 마찬가지다. Anthropic이 긴 작업의 맥락을 다루는 방법으로 든 것은 compaction, 구조화된 메모, sub-agent였다.

sub-agent는 각자 좁은 일을 맡아 수만 토큰을 쓰며 탐색하더라도 보통 1,000~2,000 토큰짜리 요약만 돌려준다. lead agent가 받는 것은 그 요약뿐이다. 같은 문서는 맥락 관리의 원칙을 "finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome"이라고 적었다.

완료 보고도 어떤 말로 적느냐에 따라 다음에 그 파일을 여는 사람이 얻는 정보가 달라진다.

넓은 보고 더 나은 보고
시스템을 고쳤다 command X 실행 뒤 warning signature Y가 사라졌다
성능이 좋아졌다 같은 조건 P에서 metric M이 baseline B에 비해 어떻게 달라졌는지 적었다
논문 답변이 준비됐다 Table 2 조건과 답변 범위를 맞췄다
repo를 이해했다 파일 A/B/C와 남은 질문 D를 확인했다

완료 보고에 다시 열어 볼 이름을 적는다. 시스템을 고쳤다 대신 어느 명령 뒤에 어떤 신호가 사라졌는지, 성능이 좋아졌다 대신 어느 조건에서 어느 지표가 어느 baseline과 견줘 어떻게 됐는지를 적는다.

오른쪽 칸의 command X, 조건 P, Table 2, 파일 A/B/C는 다음에 다시 열어 확인할 수 있는 이름이다. command X를 재실행하고 조건 P를 다시 맞추면 보고의 내용과 실제가 어긋난 지점이 드러난다.

이런 보고가 쌓이면 같은 어긋남이 두 번째로 나타났을 때 그 자리를 이름으로 찾을 수 있다. 다음 작업은 새 세션에서 시작하므로, 기록과 산출물은 파일 시스템에 남겨 두어야 다시 열 수 있다. 글뿐 아니라 그림과 데이터도 남긴다.

두 번 나타난 어긋남은 다음 세션을 시작할 때 확인할 규칙 한 줄로 옮긴다. SessionStart hook은 세션마다 한 번 실행되므로, 그 줄을 읽어 오는 일을 여기에 걸어 둘 수 있다.

규칙은 문제가 된 오류 유형에 맞춰 정한다. 원본 대신 요약만 보고 답한 적이 있으면 원본 파일을 여는 일부터 시작하게 한다. 저장소에 있는 소스 코드를 실제로 실행되는 코드로 잘못 본 적이 있으면 모듈 이름과 실제 실행 경로부터 대조하게 한다. 심사 의견에 문장만 다듬어 답하려 한 기록이 있으면 다음 세션은 주장·근거 대조표부터 만들게 한다. 이런 오류의 유형별 이름은 1장의 「연구 기록에서 경계할 오류」 표와 2부 8장의 「근거 없이 문장만 고치면 답변이 약해진다」 표에 붙여 두었다.

논문 문장, 공개 코드, 실행 결과로 각각 어디까지 말할 수 있는지는 2부에서 다룬다.

2부 실험 결과에서 논문의 주장까지

논문에 적힌 방법, 저장소에 공개된 코드, 실제 실행 기록은 각각 다른 것을 알려 준다. 논문의 방법 설명은 저자의 주장이다. 공개 코드는 지금 저장소에 어떤 구현이 들어 있는지 보여 준다. 그 코드가 논문의 실험에 쓰였는지는 코드만 보고 알 수 없다. 실행 기록은 그 코드가 지금 환경에서 어떤 경로를 지나 어떤 결과를 냈는지 남긴다.

그래서 논문과 저장소를 함께 보며 다시 실행하려면 먼저 이 세 근거를 나누어 적는다.

다시 돌려 본다는 말이 무엇을 뜻하는지는 NeurIPS 2019 Reproducibility Program 보고서에 적혀 있다. 같은 코드와, 구할 수 있다면 같은 데이터로 논문이나 발표에 실린 결과와 비슷한 결과를 얻는 일이다. 보고서는 이 일을 연구 결과를 믿어도 되는지 확인할 때 꼭 거쳐야 할 단계로 보았다.

이 프로그램의 점검표는 모델과 알고리즘, 이론적 주장, 실험 결과를 담은 그림과 표를 절을 나누어 묻는다. 내려받을 수 있는 코드를 공개했는지는 모델과 알고리즘 절에서 묻는다.

논문에 적힌 구성요소를 저장소에서 찾았다면 다음을 더 확인한다. 그 구성요소가 config를 거쳐 실제로 호출되는지, 그리고 실행 결과에 영향을 주는지다.

논문 초록과 저장소 README에도 구성요소의 이름과 역할이 적혀 있을 수 있다. 둘 다 짧게 줄인 설명이므로, 구현이 실제로 어떤 상태인지는 소스 파일과 실행 경로를 직접 확인하고 그 기록을 남긴다.

5장 논문·코드·실행은 서로 다른 근거다

확인한 내용은 표 하나에 적는다. 부록의 paper-code-experiment-map.md가 그 표이고, 논문 한 편마다 하나씩 만든다. 다시 실행하려면 먼저 어느 코드와 어느 데이터를 쓸지 정해야 한다. 저장소에서 찾은 파일이 실행할 때 실제로 지나가는 경로에 들어 있는지 살피고, 데이터는 기록에 남은 dataset과 split으로 정한다.

항목 적을 내용 채우는 시점
논문 주장 논문 표·그림의 숫자와 주장 문장 실행 전
코드 경로 저장소에서 찾아낸 파일 경로 실행 전
실제 호출 경로 돌려 봤을 때 실제로 지나간 경로 돌려 본 뒤
명령과 metric script 다시 돌려 보는 데 쓴 것 돌려 본 뒤
말할 수 있는 범위 앞의 네 항목으로 원고에 쓸 수 있는 범위 앞이 다 찬 뒤

표는 위에서 아래로 채운다. 먼저 논문 주장을 옮긴다. 어느 표와 그림에 있는 문장인지까지 적어 두면 다음에 그 표와 그림을 바로 찾아갈 수 있다.

다음 줄에는 저장소에서 이름으로 찾은 코드 경로를 적는다. 그 아래에는 실행 기록으로 확인한 실제 호출 경로를 따로 적고 두 경로를 맞대 본다. 두 경로가 같은지 다른지는 본 그대로 적는다. 이 차이는 뒤에서 구현 상태에 라벨을 붙일 때 근거로 쓴다.

명령과 metric script 줄에는 다시 실행할 때 쓴 명령과 metric script를 적는다. 말할 수 있는 범위 줄은 그 위의 줄이 모두 찬 뒤에 한 문장으로 쓰고, 원고를 쓸 때도 이 줄에 적힌 범위만 가져다 쓴다.

이 표에는 파일 내용을 옮겨 적지 않고, 다음에 열 파일의 경로만 남긴다. 논문 전문과 저장소 전체를 한꺼번에 모델에 넣으면 맥락이 길어지고, 1부에서 본 context rot 때문에 필요한 대목을 정확히 찾아 읽기 어려워진다.

표의 코드 경로 줄에 경로를 적어 두고 필요할 때 그 파일을 여는 것은 1부 4장에서 본 just in time 방식이다.

논문과 코드에서 여섯 항목을 확인한다

표를 채울 때는 아래 질문으로 논문과 저장소를 살핀다. 문서와 코드의 위치는 실행 전에 확인하고, 실제 호출 경로와 config가 쓰이는지는 실행한 뒤 기록으로 확인한다.

  1. 논문 주장이 어느 절·표·그림에 있는가
  2. 공개 코드에서 그 모듈이 어디 있는가
  3. 그 모듈이 실제 예제에서 호출되는가
  4. config key가 실행 시점에 읽히는가
  5. 논문 표의 숫자를 만든 script가 지금 저장소에 공개되어 있는가
  6. 논문 시점과 지금 branch 사이에 규약이 바뀌었는가

1번 질문의 답이 원고에서 주장할 수 있는 범위를 정한다. 모듈 경로를 찾아야 3번과 4번, 곧 실제 호출 여부와 config 사용 여부를 확인할 수 있다. 5번과 6번은 논문을 쓰던 때의 실행 규약과 지금 저장소의 규약이 같은지 묻는다.

필요한 대목만 차례로 여는 방식은 에이전트가 자료를 읽을 때도 쓰인다. Anthropic의 Agent Skills는 지시와 script와 자료를 폴더 하나에 담아 두고, 에이전트가 그 폴더를 찾아 필요할 때 불러 쓰게 한다. 폴더 내용은 단계를 나누어 연다.

폴더마다 SKILL.md가 하나 있고, 그 머리에 이름과 설명이 적혀 있다. 1단계에서는 이 이름과 설명만 시작할 때 모델에 미리 보여 준다. 2단계에서는 지금 작업과 관련 있다고 판단하면 SKILL.md 본문을 읽는다. 3단계에서는 SKILL.md가 가리키는 같은 폴더의 다른 파일을 필요할 때 연다.

Anthropic은 이 구조를 잘 정리된 매뉴얼에 견주었다. 목차에서 시작해 장으로, 다시 자세한 부록으로 내려가되 필요한 만큼만 읽는다. 앞의 여섯 질문도 답이 나온 곳에서 다음 질문으로 내려간다.

구현 상태는 증거로 분류한다

질문에 답이 모이면 모듈의 상태를 한 단어로 부를 수 있다. 실제로 구현되어 있는지, 실행을 확인했는지에 따라 아래 라벨 가운데 하나를 붙인다.

라벨 의미
active runtime에서 호출되고 결과에 영향을 준다
disabled 구현되어 있으나 꺼져 있다
configured-unused config에는 있으나 실행 경로 밖에 있다
planned-only 문서나 issue에만 있다
tested-failed 시도했으나 실패 기록이 있다
dead 남아 있으나 현재 경로 밖에 있다
unknown 확인 전

라벨은 확인한 근거와 함께 붙인다. 계획이 문서나 issue에만 남아 있으면 planned-only, flag로 꺼져 있으면 disabled로 적는다. active, configured-unused, dead는 실제로 호출되는지와 결과에 영향을 주는지를 따지므로 실행 경로를 확인해야 가를 수 있다. tested-failed에는 시도한 명령과 실패 기록이 있어야 한다.

unknown은 질문은 정했고 아직 답을 얻지 못했다는 표시다. 실행해서 근거가 생기면 알맞은 라벨로 바꾼다. 빈칸으로 두면 묻지 않은 것인지 해당 사항이 없는 것인지 알 수 없으므로, 확인할 항목에는 unknown을 쓴다.

라벨을 이렇게 나누면 파일을 읽어서 답할 수 있는 질문과, 지금 branch와 config로 실행한 출력이 있어야 답할 수 있는 질문이 갈린다. AI에 맡길 일도 이 선에 맞춰 정한다.

AI에는 논문에서 방법의 구성요소를 뽑고, 저장소에서 관련 function과 class와 config를 찾고, issue thread와 README에 적힌 규약 변화를 모으는 일을 맡긴다. 5번과 6번 질문의 답은 코드 본문 밖에 있으므로, AI가 YAML, launch command, issue comment, 실패한 sequence, 표 caption까지 확인하게 한다.

실행 결과를 봐야 답할 수 있는 항목은 사람이 확인한다. 실제로 호출되는지, config 값이 실행 경로까지 닿는지, dataset과 metric 조건이 같은지, 그 근거로 원고에서 어디까지 말할 수 있는지가 여기에 든다.

AI가 뽑을 항목은 구성요소 이름, function, config key, 규약 변화로 정해져 있다. 그러니 답을 넣을 칸의 이름과 형식을 먼저 정해 두고 그 형식에 맞는 답만 받을 수 있다.

Claude API의 structured outputs가 이 일을 한다. 답의 형식을 JSON schema로 정해 주면 모델이 그 schema에 맞는 답을 내도록 출력을 제한한다. 칸 이름을 schema로 정해 두면 돌아온 답이 그대로 표의 한 줄이 된다.

schema가 어디까지 보장하는지는 알고 써야 한다. 칸 이름과 값의 종류를 정하고, 반드시 있어야 할 칸을 지정할 수 있다. 간단한 정규식 pattern도 걸 수 있다. 수의 최솟값·최댓값이나 문자열 길이 같은 조건은 지원하지 않으므로 따로 확인한다. 모델이 답을 거절하거나 max_tokens에 걸려 답이 끊기면 schema에 맞지 않는 출력이 나올 수도 있다.

schema가 정하는 것은 필요한 칸과 값의 형식이다. 그 값이 사실인지는 따로 확인한다. 칸에 적힌 경로를 실제 실행에서 거쳤는지는 앞의 라벨과 실행 기록으로 판단한다.

논문이 말한 위치와 실행 경로의 라벨이 어긋나면 1부에서 한 것처럼 한 번에 하나씩 바꾸며 범위를 좁힌다. 좁히는 동안 다시 확인할 대상은 라벨을 붙인 근거다.

active로 적은 줄에는 그 라벨의 근거가 된 명령과 config를 함께 남긴다. 다음에 그 줄을 열면 같은 명령을 다시 실행해 라벨이 그대로인지 확인한다. 그 명령이 내놓는 숫자에는 조건을 붙여야 한다.

6장 실험 결과가 원고의 수치가 되기까지

로보틱스 metric에는 여러 조건이 붙는다. dataset과 split, sensor와 frame, calibration과 alignment, metric script, 실패 처리 방식, baseline 가운데 하나만 달라져도 같은 이름의 metric이 다른 조건을 잰 값이 된다. 두 수치를 나란히 비교하려면 이 조건이 같아야 한다.

조건이 같은지 알려면 수치를 낸 쪽이 그 조건을 함께 공개해야 한다. benchmark가 수치와 함께 평가 script, dataset 규약, 실패 처리 방식을 내놓는 것도 그래서다. 다른 사람이 같은 수를 다시 얻으려면 이 정보가 있어야 한다.

앞서 본 재현성 보고서는 코드와 데이터를 다루었다. 로보틱스에서는 sensor 입력, frame, calibration, alignment까지 적어야 한다. 원고에 오차가 낮다거나 성공률이 높다거나 지연이 짧다고 쓰려면 그 수치가 나온 조건도 함께 밝힌다.

실행 환경의 경계를 숫자로 밝힌 예도 있다. Anthropic의 code execution tool 문서는 Claude가 명령을 실행하고 파일을 다루는 sandbox를 설명한다. 이 sandbox의 메모리와 디스크는 각각 5 GiB이고 CPU는 하나다. programmatic tool calling을 쓰면 Python cell 하나에 90초의 실행 시간 제한이 걸린다.

이 sandbox에서 얻은 수치라면 이 경계값도 수치의 조건이 된다. 연구실 기계에서 잰 값이라면 그 기계의 사양이 조건으로 붙는다.

수치가 어느 기계와 dataset에서 나왔는지 나중에 되짚으려면, 실행 전에 확인할 항목을 정해 둔다. 어느 dataset의 어느 split인지, 지표는 클수록 좋은지 작을수록 좋은지, 어느 metric script와 baseline을 썼는지, 실제로 읽은 출력은 무엇인지 적는다. 이 조건을 확인할 수 있는 수치만 원고의 근거로 쓴다.

이 내용은 실행을 시작할 때 적는다. 나중에 맞추려면 명령 이력, config 파일, 결과 디렉터리를 따로 열어야 한다. 셋은 각기 다른 때의 상태를 담고 있을 수 있어서, 어느 것이 그 실행 당시의 것인지 가리기 어렵다.

먼저 수치의 조건을 적는다. 어느 dataset의 어느 split과 sequence인지, 어느 sensor로 무엇을 받아 무엇을 내는지, 정답 좌표계와 alignment는 무엇인지, metric과 기준값과 baseline은 무엇인지 남긴다.

로보틱스에서는 좌표계와 alignment가 자주 어긋난다. 같은 궤적이라도 어느 좌표계에서 오차를 재느냐에 따라 다른 양이 나온다. 추정 궤적을 정답에 맞추는 방식을 바꾸면 같은 실행에서도 오차가 달라진다. 기준값을 조금만 옮겨도 같은 실행의 성공률이 바뀐다.

조건 다음에는 같은 명령을 다시 실행하는 데 필요한 정보를 적는다. 명령과 config, 결과를 저장할 경로, 제한 시간, 실패 구간을 처리한 방식이다.

실패 구간을 어떻게 처리했는지 빠뜨리면 숫자가 실제보다 좋아 보일 수 있다. 추적을 놓친 구간을 평균에서 빼면 남은 구간만으로 평균을 내게 되기 때문이다. 결과 파일이 나오면 결과 경로도 채운다. 실행 하나에 남길 최소 기록은 여기까지다.

숫자보다 결과물의 완전성을 먼저 확인한다

실행이 끝나면 metric 값을 읽기 전에 결과물부터 확인한다. 최소 기록에 적은 것은 실행을 걸 때 정한 조건이다. 실제로 그 조건대로 실행됐는지는 나온 파일을 열어 봐야 안다. 설정과 다르게 실행돼도 metric은 숫자를 내놓으므로, 숫자부터 보면 잘못 실행된 결과를 성능으로 읽게 된다.

아래 항목은 결과 디렉터리를 처음 연 사람이 하나씩 확인할 내용이다. 모두 실행 하나만 열어 보고 답할 수 있다.

항목 확인 내용
coverage 입력 구간과 출력 구간이 서로 맞는가
output count 예상 출력 수와 실제 출력 수가 맞는가
timestamp span 시작/종료 시간이 맞는가
frame/calibration frame convention과 calibration이 같은가
preprocessing resize, crop, filtering, normalization 조건이 같은가
cache/checkpoint 현재 model과 config에서 나온 결과물인가
failure policy 실패 구간을 평균이나 집계에서 어떻게 처리했는가

coverage, output count, timestamp span으로는 실행이 끝까지 갔는지 본다. 출력 구간이 입력 구간보다 짧으면 일부 구간만 평가됐을 수 있다. 출력 수가 모자라면 중간에 빠진 부분이 있는지 살피고, 시작과 종료 시각이 예상과 다르면 실행 구간부터 다시 확인한다. 이런 차이는 metric 값만 보아서는 드러나지 않을 때가 많다.

frame/calibration과 preprocessing으로는 조건이 그대로였는지 본다. frame convention이나 calibration이 이전과 달라지면 그럴듯한 숫자가 나와도 다른 양을 잰 것이다. resize, crop, normalization이 달라지면 모델이 받는 입력이 달라진다.

cache/checkpoint 항목은 실행 환경이 요청과 요청 사이에 상태를 이어 갈 때 중요하다. 앞의 code execution tool 문서에는 상태가 남는 경우가 적혀 있다. 먼저 컨테이너다. 앞 응답의 컨테이너 ID를 다시 넘기면 같은 컨테이너를 쓰고, 그 안에 만든 파일도 남는다. 약 5분 동안 쓰지 않으면 그 상태가 저장되고, 다음 요청 때 다시 살아난다. 컨테이너는 만든 지 30일 뒤에 만료된다. 도구 버전 code_execution_20260120 이후에서 programmatic tool calling을 쓰면 Python 변수 값도 요청 사이에 남는다.

상태가 이어지면 이번 요청이 앞 요청에서 만든 변수나 파일을 그대로 읽을 수 있다. 그러면 config를 바꿨어도 결과물에 이전 상태가 섞일 수 있다. 그래서 결과물을 열어 지금 model과 config에서 나온 것인지 확인한다.

failure policy는 앞에서 본 실패 처리다. 수치와 함께 처리 방식을 확인한다.

숫자를 읽기 전에 결과물부터 연다. 설정과 다르게 실행돼도 metric은 숫자를 내놓는다. 입력 구간과 출력 구간이 맞는지, 출력 수가 예상과 같은지 먼저 확인한 뒤 값을 읽는다.

한 항목이라도 어긋나면 그 수치는 쓰지 않고 보류한다. 어긋난 항목을 최소 기록에 남겨 두면 다음에 같은 실행을 확인할 때 어디부터 열지 바로 알 수 있다.

두 실험을 비교할 조건부터 맞춘다

결과물이 맞다는 것을 확인한 뒤에 수치를 baseline이나 지난번 수치 옆에 놓는다. 그 전에 아래 항목으로 두 실행이 같은 것을 쟀는지 확인한다. output path는 실행마다 따로 확인하는 값이지만 같은 표에 두었다. 엉뚱한 결과 파일을 읽으면 다른 조건을 모두 맞춰도 비교할 수 없기 때문이다.

항목 확인 내용
task input/output 어떤 입력에서 어떤 출력을 평가하는가
ground truth 정답 파일, 좌표계, 시간 범위가 같은가
threshold success/failure를 가르는 기준이 같은가
baseline 같은 조건의 baseline인가
metric script 지난번과 같은 script인가
output path 실제로 읽은 결과 파일이 맞는가

task input/output에서는 두 실행이 처음부터 다른 문제를 풀지 않았는지 확인한다. metric 이름이 같아도 무엇을 넣고 무엇을 평가했는지가 다르면 두 값을 비교할 수 없다.

ground truth나 threshold가 다르면 같은 실행에서도 숫자가 달라진다. 정답 파일, 좌표계, 시간 범위가 달라지면 다른 양을 재게 된다.

baseline에서는 비교 대상이 같은 조건에서 나왔는지 확인한다. 다른 조건에서 잰 baseline 옆에 우리 수치를 놓으면 무엇과 견주어 올랐는지 알 수 없다.

metric script는 이름이 같아도 내부가 다를 수 있다. script가 바뀌면 같은 입력에서도 다른 값이 나올 수 있다. 다른 사람이 바꿨다면 바뀐 줄도 모르고 지나치기 쉽다.

앞의 조건을 모두 맞췄어도 마지막으로 output path가 맞는지 확인한다. 지금 읽는 파일이 그 실행의 결과여야 앞에서 맞춘 조건이 의미가 있다.

이 가운데 metric script, baseline, 결과 경로는 실행을 걸 때 최소 기록에 이미 적어 둔 항목이다. 그때 적은 값과 지금 읽는 값이 같으면 두 수치를 한 표에 넣는다.

metric script 항목에는 script 이름과 실행에 쓴 라이브러리 버전을 함께 적는다. 앞에서 본 code execution tool의 sandbox처럼 미리 설치된 패키지만 쓰는 환경이라도 실제 설치된 버전은 그 환경에서 직접 확인한다. 같은 script라도 의존성 버전이 다르면 결과가 달라질 수 있다.

원고의 수치에는 조건을 붙인다

두 표를 확인하고 나면 그 수치로 어디까지 말할 수 있는지가 정해진다. 원고에는 비교 조건이 드러나는 문장을 쓴다.

같은 dataset, 같은 sensor 입력, 같은 metric script를 쓴 baseline보다 main metric이 개선되었다.

성능이 향상되었다처럼 조건이 없는 문장은 쓰지 않고 보류한다. 오차가 낮다거나 성공률이 높다고 쓸 때는 어느 dataset과 sensor 입력에서, 어느 metric script로 계산한 baseline과 비교했는지 함께 밝힌다.

표 caption도 같다. metric 표에는 수치와 비교 조건이 함께 있어야 한다. caption에 무엇을 쓸지는 그 표가 무엇을 쟀는지에 따라 정한다.

로보틱스 원고에는 metric 표 말고도 실행 중에 일어난 사건의 횟수를 센 표가 들어간다. 이런 표가 직접 보여 주는 것은 센 횟수뿐이다. 그 결과가 다음 단계의 입력으로 쓰여 영향을 미쳤다고 쓰려면 근거가 더 있어야 한다. 표 아래 설명도 표가 뒷받침하는 범위 안에서 쓴다.

실패한 실행도 결과로 기록한다

결과 파일이 나온 실행은 결과 경로와 metric을 채울 수 있다. 중간에 멈춘 실행도 버리지 않고, 어디까지 진행됐고 무엇 때문에 멈췄는지 남긴다.

제한 시간 초과, 메모리 부족, sensor dropout, 추적 실패, 빠진 sequence, metric script 실패, 잘못된 정답 파일은 다음 실험의 조건을 정할 때 쓸 자료다. 최소 기록의 실패 처리 항목에는 집계할 때 실패 구간을 어떻게 처리했는지 적는다. 중간에 멈춘 실행은 마지막으로 끝낸 단계와 멈춘 지점을 적는다.

실패가 어디에서 일어났느냐에 따라 다음에 확인할 곳이 달라진다. 그래서 원인을 짐작하기 전에 신호가 끊긴 단계부터 가린다.

AI에 증상을 물으면 QoS, calibration, cache, normalization 같은 원인 후보를 금방 얻는다. 후보를 받자마자 고치면 지금 실행 경로를 확인하기도 전에 원인을 단정하게 된다. 어느 단계에서 신호가 끊겼는지 먼저 눈으로 확인하고, 그다음에 받은 후보와 맞대 본다.

1부에서 인간공학 연구자 Endsley가 상황 인식을 세 단계로 나눈 것을 보았다. 지금 무엇이 있는지 지각하는 단계, 그 의미를 이해하는 단계, 가까운 미래를 예측하는 단계다.

실패 기록에서는 이 이론이 지각과 이해를 구별한 점만 빌리고, 칸은 작업에 맞게 따로 둔다. 눈으로 확인한 신호, 그 신호가 끊긴 단계, 아직 검증하지 않은 원인 후보를 각기 다른 칸에 적는다. 이 세 칸을 Endsley의 세 단계에 하나씩 짝지을 수는 없다. 지난 실패의 원인 후보는 미래 상태를 예측하는 일과 성격이 다르다. 칸을 나누어 두면 관측한 사실과 짐작을 구분할 수 있다.

아래 목록들은 이 일곱 이름을 그대로 쓴다. 어느 목록을 볼지는 지금 나타난 증상으로 정한다. 입력 신호가 없을 때의 목록은 문제가 한 단계에 몰려 있을 때 원인을 빨리 좁히는 데 쓴다. 성능 저하를 추적하는 목록은 일곱 단계를 처음부터 차례로 짚을 때 쓴다.

입력 신호가 없으면 input 단계부터 차례로 확인한다

받는 쪽 callback이 비어 있다면 신호는 input에서 멈췄다. 뒤의 여섯 단계는 아직 입력을 받지 못했으니 이때 확인할 단계는 input 하나다. 고치기 전에 다음 순서로 살핀다.

  1. ros2 topic list로 topic 존재 확인
  2. ros2 topic info --verbose로 QoS 확인
  3. publisher/subscriber namespace 확인
  4. use_sim_time과 /clock 확인
  5. container device, network, volume 확인
  6. 이어서 코드 또는 launch 수정

항목 하나를 확인할 때마다 지금 단계, 관측한 신호, 다음에 볼 항목을 적는다. 1부터 5까지는 모두 input 단계 안의 확인이다. 예를 들어 topic 이름은 목록에 보이는데 callback이 비어 있다면, 다음에는 같은 단계에서 QoS profile을 본다.

1부에서 본 것처럼 driver와 받는 쪽의 QoS 설정이 맞지 않으면 메시지가 오지 않을 수 있다. 2번은 이 어긋남을 확인하는 단계다.

topic이 실제로 들어오는 것을 확인한 뒤에야 다음 단계로 preprocessing을 적는다. container device, network, volume처럼 실행 환경에서 생기는 증상은 부록 F의 로봇 실험 문제 해결 안내서에서 확인 경로를 찾는다.

1번의 ros2 topic list를 AI가 대신 실행하고 결과를 옮겨 준다면 하나를 더 확인한다. 도구가 돌려주는 응답에는 길이 제한이 있을 수 있다.

Anthropic의 도구 작성 지침은 도구가 에이전트에 꼭 필요한 정보만 돌려주어야 한다고 설명한다. 응답이 길어질 수 있는 도구에는 페이지 나누기, 범위 선택, 필터, 잘라내기를 알맞은 기본값과 함께 넣으라고 권한다.

같은 글에 따르면 Claude Code는 도구 응답을 기본 25,000 토큰으로 제한한다. Claude Code 문서는 이 제한을 MCP 도구 출력에 적용하고 MAX_MCP_OUTPUT_TOKENS 환경 변수로 바꿀 수 있다고 적는다. 예상보다 짧은 목록을 받았다면 정말 짧은 목록인지, 출력 제한에 걸린 것인지 먼저 가린다. 제한에 걸렸다면 topic 이름으로 범위를 좁혀 다시 실행한다.

성능 저하는 입력 단계부터 추적한다

성능 수치 하나가 떨어졌다면 그 값은 일곱 단계를 모두 거쳐 나왔다. 앞 절에서는 비어 있는 callback 하나로 끊긴 지점을 input으로 좁힐 수 있었다. 모든 단계를 지나 나온 값이라면 일곱 단계가 모두 후보로 남는다.

뒤 단계는 앞 단계의 출력을 받아 돌아가므로, 앞이 어긋나면 뒤도 어긋난 것처럼 보인다. 그래서 어느 단계에서 문제가 생겼는지 위에서부터 하나씩 확인한다. 고치기 전에 다음을 본다.

  1. dataset, split, sensor input 범위 확인
  2. timestamp, frame, calibration 확인
  3. preprocessing과 normalization 확인
  4. cache, checkpoint, intermediate output 확인
  5. matching, geometry, optimization의 입력과 출력 확인
  6. metric script와 failure policy 확인
  7. 이후 model architecture, training 설정, control parameter 수정

일곱 이름은 데이터가 흐르는 순서다. input으로 들어온 데이터를 preprocessing이 손질하고, representation이 다루기 좋은 형태로 바꾼다. 이어 matching이 짝을 찾고, geometry가 위치를 잡고, optimization이 전체를 맞춘다. 마지막으로 evaluation이 결과를 숫자로 잰다.

위 목록의 번호도 이 순서를 따른다. 1과 2에서는 input과 그 조건을 확인한다. 3에서는 preprocessing에 속한 normalization을 보고, 4에서는 representation이 남긴 cache, checkpoint, intermediate output을 확인한다.

5에서는 matching, geometry, optimization의 입력과 출력을 한꺼번에 확인한다. 6에서는 evaluation에 쓰는 metric script와 failure policy를 점검한다. 6장에서 숫자마다 dataset과 split과 metric script를 적어 두었다면 1과 6에서는 그 기록과 그대로 맞대 볼 수 있다. 7에서는 일곱 단계를 모두 확인한 뒤에야 model architecture, training 설정, control parameter를 고친다.

확인 결과는 같은 형식으로 적는다

앞의 두 목록에서는 항목 하나가 확인 하나다. 다음 세션에서 같은 지점을 다시 열려면 이 확인들이 한 파일에 같은 형식으로 쌓여 있어야 한다. 부록의 stage-local-debugging.md가 그 양식이다.

이 양식에서는 성공 신호와 실패 신호를 실행 전에 적는다. 무엇이 나오면 성공으로 볼지 정하지 않고 실행하면, 나온 출력에 맞춰 기준이 바뀐다. 기준은 실행 전에 적어 두어야 결과를 본 뒤에도 그대로 남는다.

실행이 끝난 뒤 채우는 칸에는 이 확인으로 말할 수 있는 것과 말할 수 없는 것을 적는다. ros2 topic list를 실행해 본 확인이라면 말할 수 있는 범위도 input 단계까지다.

눈으로 확인한 신호를 적는 칸에는 신호 하나만 적는다. 앞에서 본 도구 작성 지침은 오류 메시지를 다음에 무엇을 고쳐야 하는지 알려 주는 말로 쓰라고 권한다. 이 칸에도 traceback을 통째로 붙여 넣지 않고, input에서 어느 topic이 비어 있었는지를 적는다.

이 확인들을 한 파일에 쌓아 두면 같은 점검을 되풀이하고 있는지 볼 수 있다. 다음 단계를 적는 칸에 같은 이름이 두 번 잇달아 나오면 그사이 새로 확인한 신호가 있는지 본다. 같은 단계에 머물렀더라도 새 근거를 얻었다면 점검은 앞으로 나아간 것이다.

실행 실패와 방법 실패를 나누어 본다

같은 단계에서 새 근거 없이 점검을 되풀이했다면 그 단계 안을 한 번 더 나눈다. 같은 단계에 적힌 실패라도 종류에 따라 다음에 할 일이 다르다. 아래 표에서 실행 환경·runtime·평가 실패는 눈으로 확인한 신호로 가른다.

실패 종류 예
실행 환경 실패 pip install, CUDA driver, Docker volume, dataset path
runtime 실패 callback 없음, tf lookup 실패, node crash
평가 실패 wrong frame, wrong split, wrong metric script
방법 실패 조건을 맞춰 확인한 뒤에도 성능이 낮음

실행 환경 실패는 원인이 여러 가지다. 빌드가 성공하면 소스 코드가 컴파일된다는 것까지 확인된다. 패키지 의존성, CUDA driver, Docker volume, dataset path가 제대로 동작하는지는 따로 확인한다.

같은 명령을 code execution tool 안에서 실행했다면 환경 조건도 다르다. code execution tool 문서에 따르면 그 컨테이너는 인터넷 접근이 막혀 있어 실행 중에 패키지를 받을 수 없다. 필요한 패키지가 미리 설치되어 있는지 확인한다.

6장에서 본 것처럼 컨테이너를 다시 쓰고 있는지, 변수 값이 남아 있는지도 확인한다. 환경을 확인한 뒤에는 callback이나 tf lookup 같은 runtime 신호와 metric script 같은 평가 조건을 각각의 기록과 맞대 본다. 출력 파일은 확인 기록에 적힌 결과 경로를 직접 열어 이번 실행에서 나온 것인지 확인한다.

방법 실패는 마지막에 적는다. 실행 환경·runtime·평가 실패를 모두 배제한 뒤에야 방법 실패 줄이 남는다. 도구 실패를 방법 실패로 적으면 아직 확인하지 않은 지점이 기록에서 사라진다.

도구 실패와 방법 실패가 한 기록에 섞이면 어느 조건에서 성능이 낮았는지 흐려지므로, 부록 D의 중지 조건에 따라 원인을 다시 나눈다.

evaluation까지 확인한 기록은 성능 수치에 관한 주장을 뒷받침한다. input 단계에서 멈춘 기록은 그 지점까지 눈으로 확인한 사실만 뒷받침한다. 기록에 남은 단계와 실패 종류가 원고에 쓸 수 있는 문장의 범위를 정한다. 그 문장은 주장과 근거를 한 쌍으로 claim-evidence-map.md에 적는다.

8장 심사 의견을 주장과 근거로 푼다

심사 의견은 제출했을 때의 원고를 보고 쓴 것이다. 심사를 기다리는 동안 문장을 다듬었다면 지금 원고와 심사자가 읽은 문장이 다를 수 있다. 답변을 준비할 때는 먼저 심사 의견이 가리킨 원래 문장과 그때의 근거를 다시 찾는다.

의견을 하나 받으면 먼저 원고의 무엇을 지적했는지 가른다. 어조를 지적한 의견에는 문장을 고쳐 답할 수 있다. 실험 조건을 묻는 의견은 기존 기록으로 답할 수 있는지 확인하고, 근거가 없으면 실험을 더 한다. 주장 범위를 지적한 의견에는 근거에 맞게 범위를 줄여 답한다.

의견이 무엇을 지적했는지 가르려면 주장과 근거가 만나는 자리마다 이름이 붙어 있어야 한다. Toulmin은 The Uses of Argument에서 실제 논쟁에서 주장이 어떻게 서는지 부분을 나누어 설명했다.

논증에서 내세우는 명제를 Toulmin은 claim이라 했다(p.11). “무엇을 근거로 하는가”라는 물음에 답하는 것은 data다(p.90). 둘 사이에는 다리가 하나 더 있어야 한다. Toulmin은 그 자리에 놓이는 것을 "general, hypothetical statements, which can act as bridges, and authorise the sort of step to which our particular argument commits us"(p.91)라고 적었다. 일반적이고 가정적인 진술이 다리가 되어, 근거에서 주장으로 넘어가는 걸음을 정당화한다는 뜻이다.

이 다리를 warrant라고 한다. warrant는 그 근거가 왜 그 주장을 받치는지 말해 준다. Toulmin은 warrant가 잘 드러나지 않는다고도 적었다. "data are appealed to explicitly, warrants implicitly"(p.92). 근거는 드러내 놓고 내세우지만 warrant는 말하지 않고 넘어간다는 뜻이다.

원고에서도 data는 표와 그림으로 드러난다. 그 숫자가 왜 주장을 뒷받침하는지는 빠지기 쉽다. warrant를 문장으로 밝혀 두면 심사 의견이 근거 자체를 묻는지, 근거에서 주장으로 넘어가는 논리를 묻는지 가를 수 있다.

주장의 범위는 warrant와 다른 자리에 적는다. Toulmin이 qualifier라고 따로 둔 자리다. probably, generally, presumably처럼 주장의 세기를 낮추는 말이 여기에 온다. 이 말을 지우면 근거는 그대로인데 주장만 커진다.

의견 하나를 주장·근거 표에 옮긴다

부록 D는 원고 문장에서 출발할 때 claim-evidence-map.md를 쓰라고 적었다. 의견 하나를 이 표의 한 줄로 옮기면 다음에 할 일이 어느 칸에서 나오는지 보인다.

항목 내용
심사 의견 원문 또는 요약
문제가 된 주장 reviewer가 겨냥한 문장
현재 근거 figure, table, experiment, citation
부족한 근거 새로 필요한 실험 또는 계산
원고 수정 위치 고칠 section, table, caption, paragraph
답변 범위 답변서에서 말할 수 있는 범위
남는 한계 인정해야 할 한계

warrant는 현재 근거 칸에 근거와 함께 적는다. warrant는 그 근거가 왜 주장을 받치는지 설명하므로 근거 옆에 있어야 읽힌다.

figure와 table 이름을 적을 때는 그 숫자가 주장을 어떻게 받치는지 한 줄 덧붙인다. 그러면 읽는 사람이 머릿속으로 채우던 논리가 표 안에 적힌다. 심사 의견이 이 연결을 문제 삼는다면 기존 근거로 설명할 수 있는지 확인하고, 모자란 부분은 부족한 근거 칸에 적는다.

답변 범위에 쓸 말은 현재 근거 칸에서 나와야 한다. 그 칸으로 받칠 수 없는 말은 남는 한계로 옮긴다.

주장·근거 표는 세션 밖에 보관한다

표를 채우는 동안에는 심사 의견 원문, 지적받은 문장, 표의 숫자, 새로 실행한 결과가 한 세션에 쌓인다. 1부에서 본 compaction은 이 표에 특히 크게 영향을 준다. 칸에 적힌 것이 대개 figure와 table 이름 같은 짧은 이름이어서, 요약으로 접히면 그 이름이 무엇을 가리켰는지도 함께 사라지기 때문이다. Anthropic의 맥락 관리 cookbook은 compaction이 무엇을 요약 하나로 뭉뚱그리는지 이렇게 적었다.

user messages, assistant messages, tool calls, tool results, even prior compaction blocks are all flattened into the summary

사용자가 한 말, 모델이 한 말, 도구 호출과 그 결과, 앞서 접어 둔 요약까지 모두 새 요약 하나에 들어간다는 뜻이다. 요약을 한 번 거친 뒤에도 현재 근거 칸이 가리키던 대상을 다시 찾으려면, 그 이름이 맥락 창 밖의 파일에 적혀 있어야 한다.

이처럼 정보를 맥락 창 밖에 적어 두고 다음 세션에서 다시 읽는 방식을 memory라고 한다. 같은 cookbook은 이를 "structured note-taking"이라고 부른다. memory를 쓴 세션과 쓰지 않은 세션의 맥락 크기 차이는 1부 2장에서 보았다. claim-evidence-map.md를 파일로 두면 필요한 근거만 다시 불러올 수 있다.

파일에 옮겨 적는 일은 compaction이 일어나기 전에 마친다. Claude API의 토큰 기준 compaction에서는 compaction이 일어나는 입력 토큰 수를 설정으로 정한다. 기본값은 150K 토큰이고, 가장 낮게 잡을 수 있는 값은 50K다.

Claude Code의 hooks 문서에는 compaction 직전(PreCompact)과 직후(PostCompact)에 실행할 명령을 걸어 두는 자리가 있다. 표의 한 줄을 파일로 옮기는 일을 PreCompact에 걸어 두면, 세션이 compaction을 거친 뒤에도 같은 칸에서 다음 할 일을 꺼낼 수 있다.

근거가 갖춰진 뒤에 답변을 쓴다

표를 채우면 의견이 지적한 주장, 현재 근거, 부족한 근거가 한 줄에 나뉘어 적힌다. 이제 그 근거로 답변서를 쓸 수 있는지 판단한다.

부록 D는 멈춰야 하는 조건 가운데 하나로 “심사 위험이 남았는데 문장 다듬기만 반복한다”를 적었다. 답변 문장을 언제 써도 되는지는 아래 3번에서 정해진다.

  1. reviewer comment에서 지적받은 주장을 뽑는다.
  2. 그 주장이 기대는 table, figure, experiment, citation을 찾는다.
  3. 근거가 충분하면 답변 문장을 쓴다.
  4. 근거가 부족하면 실험, 재계산, 주장 줄이기 가운데 하나를 고른다.
  5. 원고를 고칠 자리를 답변서에 밝힌다.

무엇을 지적받았는지 정하기 전에 답부터 쓰면 엉뚱한 곳을 고치고 정작 필요한 근거는 그대로 둘 수 있다. 근거가 충분한지 먼저 판단해야 문장을 고쳐 답할지, 실험·재계산·주장 축소로 답할지 정할 수 있다.

원고에서 고칠 자리는 이 판단 뒤에 정한다. 자리부터 정하면 그 자리에 맞는 근거만 찾게 되어 순서가 뒤집힌다.

reviewer가 지적한 문장이 표의 숫자를 가리킨다면 그 표와 문장을 함께 본다. 숫자가 틀렸는지, 설명이나 주장의 범위가 틀렸는지에 따라 고칠 자리가 달라진다. 표를 고칠 때도 이 다섯 단계를 그대로 밟는다. 뽑아 둔 주장이 표 하나를 근거로 삼는다면 2번 단계에서 그 표의 칸들을 확인한다.

어떤 칸을 확인할지는 표의 내용에 따라 다르다. metric 표는 낮은 오차나 높은 성공률과 함께, 그 수치가 어느 조건에서 나왔는지도 적혀 있어야 비교할 수 있다.

이 책의 표 양식은 dataset, sensor, frame, 실패 처리를 표의 칸에 두고, split, calibration, alignment, metric script, baseline은 caption이나 본문에 적는다. 다른 양식에서는 배치가 다를 수 있다. 어디에 두든 독자가 비교 조건을 빠짐없이 확인할 수 있어야 한다. 빈 조건이 있다면 기존 실행 기록으로 채울 수 있는지, 실험을 다시 돌려야 하는지 가린다.

사건을 센 표는 같은 다섯 단계를 밟더라도 metric 표와 확인할 항목이 다르다. 센 횟수가 다음 단계에 미친 영향까지 말하려면 따로 확인할 것이 있다. 사건을 제대로 셌는지, 잘못 감지한 사건을 걸러 냈는지, 그 처리가 다음 단계가 요구하는 시간 안에 끝났는지다.

이 정보는 횟수 표에 없다. 기존 로그나 분석에서 먼저 찾고, 거기에도 없으면 실험을 더 한다. caption과 본문은 확보한 근거의 범위까지만 쓰고, 고친 자리를 답변서에 적는다.

근거 없이 문장만 고치면 답변이 약해진다

이 순서를 건너뛰어도 답변서는 쓸 수 있다. 그때 원고에 무엇이 남는지는 아래 표와 같다.

실패 결과
comment를 어조 문제로만 처리 비교 조건이나 실험 공백이 남는다
robust, general, significant를 추가 근거가 받치지 못하는 주장으로 커진다
citation만 추가 reviewer가 지적한 실험 조건 확인이 빠진다
공손한 문장부터 작성 Table, Figure, Section 수정이 빠진다

어조로만 처리하는 실패는 의견을 가르는 단계에서 생긴다. 비교 조건을 묻는 comment를 어조 문제로 받으면, 문장이 정중해진 뒤에도 그 조건은 표의 빈칸으로 남는다.

robust 같은 낱말 추가는 근거를 그대로 둔 채 주장만 세게 만드는 손질이다. citation만 추가할 때 그 citation은 다른 연구의 근거다. reviewer가 물은 것은 이 원고의 실험 조건이므로, 이 원고의 기록에서 찾거나 실험을 다시 실행해 확인한다.

다시 실행한 결과가 앞의 숫자와 같은 조건에서 나왔는지 reviewer가 확인할 근거도 답변서에 넣는다.

부록 D가 숫자를 다시 볼 때 물으라고 둔 질문에는 split, metric script, baseline이 들어 있다. 그 질문은 어느 dataset의 어느 split인지부터 묻고, 거기에 적힌 dataset이 답변 문장의 범위를 정한다. 여러 dataset에 두루 통한다는 주장을 받치는 근거가 dataset 하나에서 나왔다면 답변 문장도 그 dataset에 맞춰 쓴다. 줄인 만큼의 주장은 남는 한계 칸에 옮겨 적는다.

9장 심사와 투고에 필요한 검증

심사 의견을 누가 어떻게 썼든 답변서는 의견이 지적한 근거에 답한다. Pangram이 2025년 11월에 낸 ICLR 2026 심사평 분석은 심사평 약 7만 건 가운데 15,899건(21%)을 전부 AI가 쓴 것으로 분류했다. 이 수치는 Pangram 검출기의 판정이다. 같은 분석은 AI가 더 많이 관여한 심사평일수록 더 길고 점수를 더 후하게 준다고도 보고했다. 심사평 하나하나가 타당한지는 그 내용을 보고 따로 판단한다.

이때 할 판단은 8장과 같다. 의견이 어조를 짚는지, 비교 조건을 묻는지, 근거가 받치는 주장의 범위를 묻는지 먼저 가른다.

답변서에는 다시 돌려 볼 수 있는 이름을 적는다. baseline을 같은 조건에서 다시 맞췄다면 split, metric script, baseline 이름을 그대로 쓴다. 심사자가 실행 조건을 짚어 볼 수 있어야 한다.

참고문헌이 실제로 존재하는지 확인한다

참고문헌은 형식이 그럴듯해도 실제 문헌인지 따로 확인한다. 제목, 저자, 연도, 학회·저널명이 서로 맞는지 원문이나 출판사 페이지에서 대조한다. 원고에 남은 자리표시자와 작성 과정에서 붙인 메모도 투고 전에 따로 찾아본다.

이런 문제는 원고를 문장 단위로 다시 읽는 것만으로는 놓치기 쉽다.

투고 전에 참고문헌을 하나씩 조회한다. DOI나 제목으로 원문이나 출판사 기록을 확인한다. 링크가 열리지 않으면 서지 오류인지 접근 문제인지 다른 경로로 대조한다. 실재성과 인용 내용을 확인할 수 없는 항목은 확인 전까지 투고용 참고문헌으로 확정하지 않는다.

코드 중심 심사에는 재실행 근거가 필요하다

원고보다 실행할 수 있는 산출물을 먼저 심사하자는 제안이 있다. 저자는 코드, 데이터, 실행 환경과 함께 짧은 claim manifest를 낸다. manifest에는 주장마다 그 근거가 되는 실험 script, metric, baseline을 적는다. 필요한 하드웨어와 이미 아는 한계도 manifest에 밝힌다. 학회나 학술지가 운영하는 AI 시스템이 환경을 세우고 실험을 돌린 뒤 주장과 근거를 대조한 Review Package를 만들고, 사람 심사자는 그 결과물을 읽고 평가한다.

이 방식이 자리를 잡든 그렇지 않든 준비할 것은 같다. 주장마다 근거를 붙인 목록과, 그 근거를 다시 돌릴 수 있는 환경이다. 이 부에서 만든 표가 그 목록이 된다.

주장·근거 표를 원고와 같은 저장소에 둔다. 원고 문장 하나, 그 문장을 받치는 실행 하나, 그 실행을 다시 돌리는 명령 하나를 한 줄에 적는다.

3부 연구 절차를 에이전트 규칙으로

공개된 agent 저장소에는 연구 작업에도 쓸 만한 습관이 들어 있다. 작은 단위로 고치기, 가정 밝히기, 실패 보고, 역할 나누기, 도구 호출 기록 같은 것들이다.

이런 규칙은 대개 코드를 고치고 도구를 부르는 절차를 다룬다. 로봇 실험 수치를 다루려면 dataset, calibration, frame, metric, 실패 처리, 심사 위험까지 적어야 하므로, 외부 규칙을 가져올 때 이 항목들을 연구 환경에 맞게 보탠다.

에이전트가 도구를 언제, 어떻게 부를지는 1부 4장에서 잠깐 보았듯 연구에서도 다뤄 왔다. 여기서는 그 두 연구를 조금 더 자세히 본다. Yao 등의 ReAct는 집안일 지시를 따르는 과제(ALFWorld)와 온라인 쇼핑 과제(WebShop)에서 모방학습·강화학습으로 훈련한 방법보다 성공률이 각각 34%p와 10%p 높았다.

ReAct는 추론과 행동을 번갈아 적은 예시를 프롬프트에 넣어 모델이 다음 행동을 고르게 했다. Schick 등의 Toolformer는 API 호출이 들어간 자료로 모델을 학습시켰다. 모델은 어떤 API를 언제 부를지, 어떤 값을 넘길지, 돌아온 결과를 다음 토큰 예측에 어떻게 쓸지 배웠다.

두 연구 모두 도구를 부르고 그 결과를 다시 추론에 넣었다. 어느 dataset의 어느 split을 쓸지, 어느 metric script로 잴지는 여전히 연구자가 정한다. 이 조건이 빠진 채 외부 규칙을 그대로 옮기면 서로 다른 실험을 같은 결과처럼 비교하게 된다.

무엇을 어디에 적을지는 작업이 돌아가는 구조를 보고 정한다. Anthropic은 Managed Agents 글에서 에이전트를 세 부분으로 나눴다. session은 일어난 일을 순서대로 덧붙여 쌓는 기록이다. harness는 모델을 호출하고, 모델이 요청한 도구 호출을 알맞은 실행 환경으로 넘기는 loop다. sandbox는 코드가 돌고 파일이 고쳐지는 실행 환경이다.

연구 workspace도 이렇게 나눌 수 있다. 어느 파일을 먼저 읽고 어떤 결과에서 멈출지 정한 규칙은 harness에 속한다. 다음 작업에서 다시 읽을 기록은 session에, 실제 파일과 command와 dataset이 놓인 실행 환경은 sandbox에 속한다.

외부 저장소의 규칙을 가져올 때는 먼저 문장마다 session, harness, sandbox 가운데 어디에 속하는지 가른다.

10장 외부 에이전트 규칙을 연구에 맞춘다

저장소의 star 수로는 관심을 얼마나 받았는지만 알 수 있다. 규칙이 지금도 지켜지는지, 연구 작업에 옮길 만한지는 규칙을 직접 읽고 판단한다.

무엇을 가져올지는 저장소 유형에 따라 다르다. skill 모음에서는 쓸 만한 습관 문장을 가져오고, framework 문서에서는 역할을 나누고 도구를 넘기는 방식을 참고한다. 유형별로 살필 항목을 표에 적었다.

유형 예 볼 것
coding-agent skill repo multica-ai/andrej-karpathy-skills 작은 수정, 가정 명시, 범위 제한, 실패 보고
agent 개념 입문 repo datawhalechina/hello-agents agent, memory, tool use, evaluation 항목
framework 문서 LangGraph, CrewAI, AutoGen, OpenAI Agents SDK workflow, role 분리, tool handoff, tracing
local research agent repo alexjunholee/robotics-research-agent user reaction prior, 연구 증거 확인 규칙

표의 coding-agent skill repo는 작업 습관을 다시 쓸 수 있는 단위로 묶어 둔 저장소다. Anthropic은 Agent Skills를 지시, 스크립트, 자료를 한 폴더에 담아 두고 에이전트가 필요할 때 불러 쓰는 방식이라고 설명했다.

폴더마다 SKILL.md가 하나 들어 있고, 파일 맨 위에 이름(name)과 설명(description)을 적는다. 에이전트는 시작할 때 설치된 모든 skill의 이름과 설명만 읽어 두었다가, 지금 작업에 맞는 skill이 있으면 그 SKILL.md 전체를 읽는다. 이름과 설명은 skill을 만든 사람이 쓴다. 그 skill을 연구 작업의 어느 단계에서 부를지는 규칙을 가져오는 사람이 정한다.

표의 볼 것 칸에 적힌 항목도 session, harness, sandbox로 나눈다.

작은 수정, 가정 밝히기, 실패 보고, 역할 나누기, 도구 넘기기는 에이전트가 단계마다 따를 문장이므로 harness에 둔다. 도구 호출을 나중에 되짚을 수 있게 남긴 기록(tracing)과 사용자가 전에 무엇을 반려했는지 적은 기록(user-reaction-prior.md)은 다음 작업에서 다시 읽으므로 session에 둔다. 실제 저장소, 데이터셋, 명령은 sandbox에 둔다.

규칙 파일에는 에이전트의 행동을 실제로 바꾸는 문장만 넣는다. 입문 저장소에 나오는 memory나 evaluation 같은 개념은 이 분류를 이해하는 데만 참고한다.

그래서 코딩 규칙은 AGENTS.md로 옮기고, 교육용 저장소에서는 학습 자료의 구성만 참고한다. 도구 목록은 필요한 기능을 찾을 때 쓴다. 로보틱스 연구 규칙에는 데이터셋, 지표, 출력, 주장, 심사 위험 항목을 더한다.

일반 코딩 규칙에는 로봇 실험 정보가 빠져 있다

로봇 실험 수치를 두고 말하려면 아래 항목이 더 있어야 한다.

  • dataset, split, sequence
  • task input/output
  • ground-truth frame
  • metric script
  • failure policy
  • implementation status
  • result provenance
  • 원고에서 말할 수 있는 범위

1부와 2부에서 다룬 이 항목 가운데 dataset부터 failure policy까지는 실행을 시작할 때 채우는 최소 기록이고, sandbox 안의 파일과 script를 가리킨다.

implementation status, result provenance, 원고에서 말할 수 있는 범위는 실행 결과를 해석할 때 채운다. implementation status는 논문의 주장과 실제 실행 경로를 맞대 보고 적는다. result provenance에는 그 수치가 어떤 실행에서 나왔는지 적는다. 마지막 항목에는 이 근거로 원고에서 어디까지 말할 수 있는지 적는다.

외부 저장소에서 가져온 문구 옆에는 이 항목들을 따로 붙인다. 빠뜨리면 조건이 다른 수치를 같은 실험처럼 비교하게 된다. 부록 D(PATH.md)는 실험 조건이 바뀌었는데 숫자를 비교하려 한다를 멈춰야 할 때 가운데 하나로 적어 두었다.

이런 실수는 실행 오류를 내지 않을 때가 많다. 조건을 바꾼 뒤에도 이전 조건에서 만든 cache를 그대로 읽거나, 이름만 같은 metric script 둘의 결과를 한 표에 올리면 숫자는 나오지만 비교할 근거가 없다. 실행 조건과 provenance를 함께 적어 두어야 이런 어긋남을 찾을 수 있다.

원고에서 말할 수 있는 범위는 뒤에서 claim-evidence-map.md에 주장과 근거로 나누어 적는다.

외부 규칙은 기능별로 나누어 가져온다

외부 prompt 하나에는 도구를 부르는 법, 다음 세션에 남길 상태, 계속 지킬 행동 규칙이 한데 섞여 있을 때가 많다. 이를 통째로 옮기면 나중에 한 가지만 고치거나 바꾸기 어렵다.

그래서 문장마다 무슨 일을 하는지부터 본다. Model Context Protocol(MCP)은 AI 애플리케이션에 기능을 붙이는 프로그램을 server라고 부른다. server가 내놓는 요소 가운데 tool은 호출해서 동작을 시키는 함수, resource는 읽어서 맥락으로 쓰는 자료, prompt는 대화를 짤 때 다시 쓰는 틀이다.

가져올 문장에도 같은 질문을 한다. 이 문장은 실행되는가, 자료로 읽히는가, 다시 채워 쓰는 틀인가?

  1. 외부 repo의 규칙을 기능별로 나눈다.
  2. Claude, Cursor, Codex 같은 특정 도구에 묶인 호출법을 떼어 낸다.
  3. 다음 작업에도 남겨야 할 상태는 project-memory.json, ledger, replay case로 옮긴다.
  4. 남는 행동 규칙은 AGENTS.md나 template에 정리한다.
  5. 실제 실행 경계(repo, dataset, artifact, command)를 정한다.
  6. dataset, metric, 결과물, reviewer risk 항목을 더한다.
  7. 사용자가 여러 번 반려한 패턴을 문서 앞쪽에 둔다.

1단계에서 문구를 기능별로 나누고, 2단계에서 특정 도구 이름에 묶인 호출법을 떼어 내면 필요한 기능만 다시 조합할 수 있다. Anthropic의 도구 작성 지침도 여러 동작을 도구 하나로 묶거나, 관련 도구에 같은 이름 앞머리를 붙여 범위를 드러내라고 권한다.

가져온 규칙도 기능에 따라 이름을 붙여 묶는다. dataset 규칙과 원고 규칙을 따로 두면 다음 요청에서 어느 부분을 읽어야 할지 바로 보인다.

tool·resource·prompt로 문장을 나눈 뒤에는 session·harness·sandbox 가운데 둘 곳을 정한다. 다음 작업에서 다시 읽을 기록은 session에, 작업마다 따를 행동 규칙은 harness에, 규칙이 다루는 저장소·dataset·결과물·명령은 sandbox에 둔다. 특정 도구의 호출법은 그 도구의 저장소에 남긴다.

5단계의 실행 경계는 로봇을 다룰 때 더 넓어진다. 로봇은 코드가 도는 컴퓨터 밖에서 움직이므로 장치, 시계, 네트워크의 현재 상태도 이 경계에 들어간다. 이 상태를 적는 방법은 다음 장에서 다룬다.

6단계에서는 앞에서 정리한 실험 항목을 더한다. 이 항목이 있어야 규칙을 옮긴 뒤에도 로봇 실험의 조건과 수치를 따라갈 수 있다.

7단계에서는 사용자가 여러 번 반려한 패턴을 규칙 앞쪽에 둔다. 에이전트가 작업을 시작하면서 먼저 읽어야 같은 실수를 덜 한다.

이렇게 정리한 규칙은 AGENTS.md와 template에 들어가고, 다음 요청부터 에이전트가 읽는다.

반복된 오류는 다음 규칙으로 남긴다

규칙을 지켰는지는 산출물을 보고 확인한다. 그래서 답을 내기 직전에 점검할 항목도 규칙에 넣는다. 부록 B의 첫 요청에는 원문이나 산출물이 있으면 요약만 보고 현재 상태를 단정하지 말라는 문장이 있다. 작업 전에 읽은 규칙을 마지막에 다시 확인하게 하려는 문장이다.

답을 내기 직전에 스스로 점검할 항목을 규칙에 넣어 둔다. 읽지 않은 파일을 읽은 것처럼 말했는지, 근거보다 넓은 주장을 썼는지, 실행해야 할 때 계획만 말했는지를 그 자리에서 본다.

가져온 규칙에도 마지막 점검을 둔다. 위 상자의 세 항목에 더해, 사용자가 반려한 문체나 구조를 되풀이했는지, 공개 문서에 내부 작업 기록을 남겼는지 확인한다.

문제가 보이면 먼저 산출물을 고친다. 같은 항목이 두 번째로 걸리면 AGENTS.md에 규칙 한 줄을 더하거나 replay case로 남긴다. 이 기록을 보면 어떤 규칙이 실제로 오류를 줄였는지도 알 수 있다.

가져온 규칙을 계속 쓸지는 metric 혼동, cache 실수, 되풀이되는 reviewer comment가 실제로 줄었는지 보고 정한다. 이를 확인하려면 규칙을 적용한 로봇 환경의 상태와 결과를 함께 기록해야 한다.

11장 로봇 실험의 조건을 기록한다

10장의 5단계에서 실행 경계를 정하라고 했다. 로봇에서는 하드웨어, OS, 네트워크, 실시간 조건이 함께 작동하므로 이 경계가 코드 밖까지 이어진다.

에이전트는 질문에 담기거나 연결된 도구가 넘겨준 관측값만 안다. 장치와 실행 상태를 알려 주어야 에이전트가 지금 로봇의 조건에 맞춰 답을 좁힌다.

그러므로 질문을 쓰기 전에 토픽, 장치, 시계, 네트워크, 권한, 시스템 구조의 현재 상태를 먼저 적는다. 이 관측값이 있어야 답이 그 자리에서 실행할 확인 절차로 좁혀진다.

에이전트가 코드를 직접 실행하는 sandbox는 문서에 조건이 나와 있다. Anthropic의 code execution tool 문서에 따르면 메모리와 디스크가 각각 5 GiB, CPU가 하나이고 인터넷 접속이 막혀 있다. 무엇을 할 수 있고 없는지가 숫자로 먼저 드러난다.

로봇의 규격과 설정도 문서에서 찾을 수 있지만, 그것만으로는 지금 이 기계가 어떤 상태인지 알 수 없다. 어떤 장치가 연결되어 있는지, 시계가 맞는지, 네트워크가 어디까지 닿는지는 현장에서 직접 확인한다.

시행 횟수와 불확실성을 함께 본다

장치와 시계, 네트워크를 확인했으면 실행하기 전에 시행 횟수와 비교 방법을 정한다. 시행 횟수는 구별하려는 차이와 받아들일 불확실성에 맞춰 정한다. 성공률은 시행 횟수와 함께 적는다. 17/20과 14/20은 각각 85%와 70%인데, 분모가 있어야 두 값이 얼마나 불확실한지 판단할 수 있다.

성공률 옆에 시행 횟수와 불확실성을 같이 적는다. 17/20처럼 분자와 분모를 남기고, 두 정책을 비교할 때는 같은 방법으로 계산한 구간이나 검정 결과를 함께 적는다.

비교 설계를 바꾸는 방법도 있다. RoboArena 연구진은 학술기관 일곱 곳에서 DROID 로봇으로 정책 일곱 개를 짝지어 600회 넘게 이중맹검으로 비교했다. 평가자는 과제와 환경을 각자 골랐고, 두 정책을 나란히 돌려 본 뒤 어느 쪽이 나은지 답했다. 연구진은 시험한 모든 과제에서 모든 정책을 돌려 기준 순위를 따로 만들었다. 짝비교로 얻은 순위는 고정된 표준 과제로 얻은 순위보다 이 기준 순위에 더 가까웠다.

시뮬레이션을 섞는 방법도 있다. SureSim은 시뮬레이션을 많이 돌리고 실기는 적게 돌린 뒤, 둘 사이의 차이를 보정해 실기 성능의 신뢰구간을 낸다. diffusion policy와 π0를 물리 시뮬레이션으로 시험한 실험에서는 비슷한 폭의 구간을 얻는 데 드는 실기 시행을 20~25% 넘게 줄였다.

두 방법 모두 기록이 있어야 쓸 수 있다. 짝비교에서는 두 정책을 어떤 환경에서 비교했는지 적는다. 시뮬레이션 보정에서는 같은 조건을 실기와 시뮬레이션 양쪽에서 돌렸다는 기록을 남긴다.

자동 실험의 판정은 원자료를 다시 열어 검증한다

자동 실험에서는 모델이 다음 실험을 제안하고, 장비가 데이터를 만들고, 채점 결과가 다시 다음 선택에 들어간다. 이 고리가 계속 돌았다고 해서 채점이 옳았다고 볼 수는 없다. 생성과 검증에 같은 판정 절차를 쓰면 그 절차의 오류가 다음 실험으로 넘어간다.

버클리의 A-Lab이 그런 예다. 합성과 X선 회절(XRD) 무늬 판정은 자동 고리 안에서 이뤄졌다. 논문이 나온 뒤 회절 판정과 신물질 주장에 문제가 제기되자, 연구진은 같은 회절 원자료를 사람이 다시 분석했다. 연구진이 2026년 1월에 낸 정정문(author correction)에 따르면 자동 판정이 성공이라고 보고한 40건 가운데 36건은 판정이 맞았고 4건은 회절 자료만으로 판단할 수 없었다.

검증은 이렇게 한다. 실행 조건과 성공 기준을 먼저 정해 둔다. 실행하는 동안 원자료와 실패 기록을 보존한다. 자동 판정이 읽은 입력과 적용한 규칙을 남긴다. 고리 밖에서 원자료를 열어 판정을 다시 확인한다. 무엇을 변수로 두었는지, 어디까지 성공으로 셌는지, 실패한 실행을 집계에서 어떻게 다뤘는지도 같은 기록과 맞대 본다.

로봇 실험에서는 장치 연결, 시계, 네트워크 상태에 따라 같은 명령도 결과가 달라질 수 있다. 실험 규칙에는 자동 고리의 실행 조건, 원자료, 판정 절차를 다시 확인할 시점을 정해 둔다.

증상에 맞는 첫 확인 명령을 찾는다

토픽이 오지 않을 때, 컨테이너에서 장치가 보이지 않을 때, 드라이버가 아무 반응도 하지 않을 때는 각각 먼저 실행해 볼 명령이 있다. 부록 F의 로봇 실험 문제 해결 안내서에 이 명령들을 증상별로 모아 두었다.

첫 항목은 1부 2장에서 본 QoS(통신 품질 설정) 불일치다. 안내서는 먼저 ros2 topic info /camera/image_raw --verbose를 실행하고 출력의 Reliability와 Durability 줄을 보라고 한다. 토픽이나 driver를 의심하기 전에 이 두 줄부터 확인한다.

다른 항목도 같은 형식으로, 증상마다 먼저 실행할 명령 하나와 그 출력에서 볼 줄을 적어 두었다. 어떤 증상이든 질문을 쓰기 전에 그 명령으로 현재 상태를 적고, 적은 내용을 에이전트에게 준다.

12장 에이전트에게 맡길 일과 사람이 잴 일

에이전트는 질문에 담긴 환경 정보와 관측 자료를 바탕으로 답한다. 같은 증상이라도 무엇을 함께 알려 주느냐에 따라 답이 달라진다.

"카메라가 안 돼요"라고만 물으면 지금 쓰는 기계와 상관없는 원인 목록이 돌아온다. 같은 증상을 이렇게 적으면 답의 범위가 좁아진다.

Ubuntu 22.04, ROS2 Humble, Intel RealSense D435를 쓴다. rs-enumerate-devices에서는 보이지만 ros2 launch realsense2_camera rs_launch.py를 실행하면 Could not open device 오류가 난다. Docker 안에서 실행 중이고, --device=/dev/video0은 매핑했다.

자세히 적은 질문에는 장치가 한 도구에서는 보이는데 다른 실행 환경에서는 열리지 않는다는 관측이 들어 있다. 이 정보가 있으면 드라이버만 의심하지 않고 컨테이너의 장치 접근 설정부터 확인할 수 있다.

그래서 물을 때마다 아래 항목을 함께 적는다.

  • OS 버전, ROS 버전
  • 하드웨어 플랫폼 (x86 vs ARM/Jetson)
  • 센서 모델명
  • 오류 메시지 전문
  • ros2 topic list, ros2 node list 출력
  • Docker 사용 여부와 실행 옵션 (docker run 명령 전체)
  • 네트워크 구성 (유선/무선, IP 대역)

오류 메시지는 원문 그대로 옮긴다. Could not open device 같은 문자열은 그대로 검색할 수 있는데, "카메라가 안 열린다"로 줄여 쓰면 검색어가 사라진다.

docker run 명령도 통째로 복사한다. 장치, 네트워크, 볼륨을 어떻게 넘겼는지가 모두 들어 있어서, 손으로 옮겨 적으면 빠지는 정보가 생긴다.

오류 메시지와 docker run 명령은 통째로 옮긴다. 오류 문자열은 그대로 검색어가 되므로 요약하지 않는다. docker run 명령줄에는 장치·네트워크·볼륨 매핑 정보가 모두 들어 있다.

나머지 항목은 답을 지금 쓰는 기계와 구성에 맞게 좁힌다. OS와 ROS 버전에 따라 패키지 이름과 기본값이 정해진다. 하드웨어 플랫폼에 따라 특정 패키지를 쓸 수 있는지가 갈린다. 센서 모델명을 알면 어느 드라이버를 볼지 정할 수 있다. ros2 topic list와 ros2 node list 출력을 보면 노드가 아예 뜨지 않았는지 다른 이름으로 떴는지 알 수 있다. 네트워크 구성은 여러 장치가 어떻게 연결되어 있는지 알려 준다.

제안을 실행하기 전에 현재 환경과 맞는지 확인한다

돌아온 답에는 실행해 볼 명령이나 바꿀 설정이 들어 있다. 실행하거나 설정을 바꾸기 전에 확인할 것은 제안의 종류에 따라 다르다.

패키지를 설치하라는 제안이면 그 패키지가 지금 쓰는 ROS와 Ubuntu 버전을 지원하는지 먼저 확인한다. apt search ros-humble-PACKAGE_NAME 같은 명령을 쓴다.

설정을 바꾸라는 제안이면 현재 설정부터 백업한다. 그다음 그 제안이 어떤 관측 결과를 설명하려는지 본다. 설명하려는 관측이 있어야 바꾼 뒤에 무엇이 나아졌는지 잴 수 있다.

환경을 다시 설치하라는 제안이면 그 전에 현재 상태를 기록한다. pip show, dpkg -l | grep, apt policy로 설치된 항목과 충돌 범위를 남긴 다음 손댄다. 다시 설치하고 나면 이 기록만이 이전 상태를 알려 준다.

코드를 받았으면 다른 사람의 기계에서만 돌아가는 부분이 섞여 있는지 본다. 하드코딩된 경로(/home/user/...), IP(192.168.1.100), x86 전용 패키지(amd64 wheel) 같은 것들이다.

초안은 맡겨도 현장 상태는 직접 측정한다

왼쪽 칸의 일은 문서와 코드만으로 초안을 만들 수 있다. 오른쪽 칸의 일은 하드웨어와 소프트웨어가 맞닿는 곳에서 생기므로, 장치 상태와 타이밍, 패킷처럼 지금 이 기계에서 얻은 관측 자료가 있어야 답할 수 있다. 먼저 직접 측정하고, 그 결과를 에이전트에게 분석 자료로 준다.

13장 연구 단계의 역할을 나누고 하네스를 점검한다

에이전트의 산출물은 확인하기 전까지 초안이다. 논문 읽기, 코드 작성, 실험 설계, 원고 작성은 작업마다 오류가 드러나는 곳이 달라서, 초안을 확인할 자료도 다르다.

논문은 원문을 먼저 읽는다

중요한 논문은 세 번에 나누어 읽는다. 에이전트의 요약은 원문을 직접 읽은 뒤에 보조 자료로 쓴다. 요약부터 읽으면 요약이 고른 내용에 눈이 가서, 원문에서 확인할 범위도 좁아지기 쉽다.

읽으면서 채울 칸은 부록의 paper-reading-note.md에 있다. 방법의 가정은 따로 적는다. 관측 모델을 어떻게 두었는지, 데이터에 무엇을 전제했는지는 원문에서 확인한다. 원문을 읽고 채운 내용이 요약과 다르면 그 대목을 다시 읽는다. 이렇게 읽는 방법은 「연구노트」의 논문을 세 번에 나누어 읽기와 마음가짐에서 다룬다.

코드는 실행 조건을 함께 준다

프로토타입을 요청할 때는 실행 조건과 기준값을 적는다. 어떤 데이터셋에서 어떤 특징점을 뽑아 어떻게 매칭할지, 어느 라이브러리를 쓰고 기준값을 얼마로 둘지 적는다. 조건을 비워 두면 받은 코드가 어떤 기본값을 골랐는지 다시 확인해야 한다.

디버깅할 때는 오류 메시지와 관련 코드를 함께 주고, 가능한 원인과 확인할 순서를 묻는다. 순서까지 받아 두면 어디까지 점검했는지도 남는다. 구조를 바꾸는 작업은 바꾸기 전후의 동작을 테스트로 확인할 수 있어서 맡기기 쉽다.

직접 확인할 항목은 앞의 표 오른쪽 칸에 있다.

실험은 빠진 비교 축을 찾는다

실험을 설계할 때는 baseline 비교 표를 주고, 빠진 비교 축의 후보를 묻는다. 제안받은 축이 연구 질문과 자원에 맞는지는 사람이 다시 고른다. 필요한 비교를 설계 단계에서 찾아 두면 심사 뒤에 실험을 다시 돌리는 일을 줄일 수 있다. 실험 설계와 ablation, 결과 해석에 에이전트를 쓰는 방법은 「연구노트」의 Revision/Rebuttal에서 다룬다.

원고 초안은 문장과 서지를 다시 확인한다

초고를 쓸 때는 핵심 아이디어와 실험 결과를 주고 Introduction의 논리 구조를 제안받을 수 있다. 영어 문장은 문법과 문맥을 함께 봐 달라고 한다. 받은 문장은 근거와 문맥을 확인한 뒤 원고의 목소리에 맞춘다. 한 논문 안에서 문단마다 어조가 다르면 읽는 사람은 논리보다 그 차이를 먼저 알아챈다.

서지 항목은 특히 조심한다. 모델이 내놓는 연도와 학회명은 형식이 그럴듯해서 읽기만 해서는 오류가 보이지 않을 수 있다. 잘못된 인용은 원고 전체의 신뢰를 떨어뜨리므로, 초안을 받으면 논문 원문이나 출판사 페이지에서 연도, 학회·저널명, 권·호를 하나씩 확인한다.

작업이 바뀔 때마다 초안과 확인된 사실을 나눈다

논문 읽기, 코드 작성, 실험 설계, 원고 작성은 하루 안에서도 번갈아 이어진다. 아침에 논문 요약을 확인하고, 낮에 코드를 고치고, 저녁에 관련 연구 표를 정리하는 식이다. 작업이 바뀌어도 앞서 본 내용이 머리에 남아 있어서, 한 작업의 요청이 다른 작업으로 번지기 쉽다.

부록의 weekly-research-ledger.md는 이렇게 흩어진 작업을 주 단위로 정리한다. 그 주에 나온 수치를 한 줄씩 적고, 줄마다 원고에 쓸 수 있는지 표시한다. 원고에는 표시한 수치만 쓴다.

같은 장부에는 연구를 진전시킨 일과 환경을 구축한 일도 따로 적는다. 도구를 연결하고 데이터를 옮기느라 바빴던 날에도 새 주장은 하나도 늘지 않았을 수 있다. 두 칸을 나누어 적어야 그런 날이 보인다.

작업을 바꿀 때마다 무엇이 초안이고 무엇이 확인된 사실인지 표시해 둔다. 에이전트가 만든 비교 표에서 두 논문의 방법이 뒤바뀌지 않았는지는 원문을 열어 확인하고, 이 확인은 결과물을 검토하는 사람이 맡는다.

여섯 요소로 연구 하네스를 점검한다

서문에서는 하네스를 여섯 요소로 나누었다. 1부부터 3부까지 다룬 내용을 이 요소에 맞춰 보면 다음과 같다.

  • 관측은 에이전트에게 무엇을 보여 줄지 정한다. 2부에서 숫자보다 결과물을 먼저 여는 습관과 실패 원인을 입력 단계부터 좁히는 순서가 여기에 들어간다.
  • 문맥은 그 가운데 무엇을 이번 요청에 넣을지 정한다. 1부에서 다룬, 세션을 나누어 이어 가는 규칙과 확인한 사실을 파일에 적어 두는 습관이 여기에 들어간다.
  • 제어는 어떤 주기로 돌리고 언제 멈출지 정한다. 원 연구는 일을 누구에게 넘기고 어떤 역할을 맡길지도 제어에 넣었다. 3부에서 에이전트에게 맡길 일과 사람이 잴 일을 가르고 연구 단계마다 역할을 나눈 내용이 여기에 들어간다.
  • 행동은 무엇을 실행하게 할지 정한다. 3부에서 외부 규칙을 기능별로 나누어 AGENTS.md에 옮기는 절차와 증상마다 먼저 실행할 확인 명령이 여기에 들어간다.
  • 상태와 산출물은 무엇을 남길지 정한다. 1부에서 대화 밖에 남기는 기록과 긴 작업의 단계마다 남기는 기록이 여기에 들어간다.
  • 검증과 통치는 무엇으로 확인하고 무엇을 막을지 정한다. 2부에서 두 실험의 비교 조건을 맞추고, 참고문헌이 실제로 있는지와 코드를 다시 돌린 근거가 있는지 확인하는 일이 여기에 들어간다.

모델의 산출물만 보고는 그것이 맞는지 판정할 수 없으므로, 검증과 통치에는 모델 밖의 기준이나 자료가 있어야 한다. 나머지 요소는 이 판정에 쓸 자료와 실행 경로를 남긴다. 제어 역시 미리 적어 둔 중지 조건과 검증 결과를 읽고 다음 행동을 정한다. 중지 조건에 닿았을 때 실제로 멈출 수 있는지, 다음 사람이 기록만 열어 같은 조건을 다시 확인할 수 있는지도 이때 살핀다. 그래서 연구 하네스를 꾸릴 때는 모델을 고르기 전에 무엇을 보여 주고, 무엇을 남기고, 무엇과 대조할지부터 정한다.

부록 A — AI 연구의 용어·근거·작업 구조

AI 도구를 연구에 쓰다 보면 역할이 다른 모델, 도구, 에이전트, 기억 기록을 한데 묶어 생각하기 쉽다. 이 경계가 흐려지면 실험 수치와 원고의 주장도 함께 흔들린다. 아래 표에 각 용어가 가리키는 대상과 근거로 삼을 수 있는 범위를 적었다.

AI 연구의 기본 용어

용어 뜻 조심할 점
모델 텍스트, 코드, 이미지, 표를 생성하거나 판단하는 기반 모델 모델의 답변은 현재 작업 공간을 다시 확인할 출발점으로 쓰고, 상태는 원본 파일로 확정한다
도구 파일 읽기, 명령 실행, 검색, 이미지 생성처럼 모델 밖에서 일을 하는 기능 도구 결과는 해당 명령이나 API의 범위 안에서만 근거가 된다
에이전트 모델과 도구를 묶어 여러 단계를 처리하는 실행자 연구 주장은 실행 결과로 뒷받침한다
스킬 정해진 상황에서 에이전트가 따르는 절차와 판단 기준 작업자는 스킬을 사용할 조건을 확인한다
하네스 상태, 근거, 행동, 확인, 주장을 잇는 운영 구조 한 번의 AI 작업 결과로 주장할 수 있는 범위를 제한한다
AGENTS.md 에이전트가 작업 전에 읽는 저장소 규칙 한 번의 요청이 끝난 뒤에도 프로젝트 규칙으로 남는다
기억 기록 현재 상태, 반복 위험, 계속 적용할 사용자 교정 사항을 보관하는 기록 근거를 다시 확인할 위치를 알려 주는 자료다
변경 이력 실험, 주장, 교정 사항, 반복 확인이 어떻게 바뀌었는지 남긴 기록 다음 행동의 범위를 정할 때 쓴다
반복 확인 같은 실패가 다시 발생하는지 확인하는 작은 시험 다음 작업 전에 반복 실수를 찾는 데 쓴다
실험 조건 dataset, split, metric, baseline, output path 등 수치를 비교할 때 함께 확인하는 항목 수치는 이 조건 안에서만 비교한다
결과물 파일, 로그, 표, 그림, 체크포인트, 명령 출력 출처와 함께 읽어야 한다
주장 원고, 답변서, README, 발표에서 독자에게 제시하는 판단이나 결론 근거 범위를 넘어서면 안 된다

근거 단계와 주장 범위

단계 예 말할 수 있는 범위
방향 잡기 이전 요약, 기억 기록, 인계 메모 어디를 다시 볼지 정한다
확인 대상 파일명, 이슈 제목, 검색 결과 원인이나 다음 확인 대상을 제안한다
관찰 원본 파일 일부, 로그 일부, 설정 일부 직접 본 범위 안의 사실을 말한다
실행 결과 명령 실행 결과, 생성된 파일 그 실행의 결과를 말한다
실험 조건 확인 dataset, split, metric, baseline, output path를 확인한 숫자 같은 조건 안에서 비교한다
원고 주장 그림, 표, 인용, 심사 위험을 함께 확인한 문장 원고와 답변서에 쓴다

AI는 이 단계를 건너뛴 답을 내놓을 수 있다. 요약을 근거처럼 쓰거나, 한 번의 실행 결과를 방법이 나아졌다는 증거로 내세우기도 한다. 로그 일부만 보고 전체 실행의 원인을 단정할 때도 있다.

도구별 역할과 확인 항목

도구 좋은 용도 확인할 항목
대화 모델 개념 정리, 논문 질문, 주장 분리 답변이 원본 파일 확인에 근거하는지 살핀다
코딩 에이전트 저장소 읽기, 작은 수정, 스크립트 실행 원본 파일, 명령 출력, 변경 내용을 남긴다
IDE 보조 도구 한 파일 안의 짧은 편집과 이름 변경 변경 범위와 포매터·테스트를 확인한다
브라우저·검색 도구 외부 저장소, 논문, 문서 발견 링크, 확인일, 주장 범위를 남긴다
터미널·스크립트 빌드, 지표 산출, 체크섬 확인 실행 명령과 출력 경로를 남긴다
프로젝트 기억 기록 계속 적용할 교정 사항과 현재 상태 보관 기억 기록은 증거 위치를 찾는 단서로 쓴다

도구가 바뀌면 근거의 무게도 다시 따져 본다. 검색 결과는 아직 후보일 뿐이다. 터미널 명령을 실제로 실행한 기록이 있어야 실행 결과로 볼 수 있다. 수치는 dataset, split, metric script를 확인한 뒤 원고에 쓴다.

MCP의 tool·resource·prompt

새 도구를 붙일 때도 실행할 기능, 읽을 자료, 다시 쓸 틀을 나눈다. Model Context Protocol(MCP)에서 host는 server마다 client를 하나씩 만들어 따로 연결한다. server가 내놓는 요소는 실행하는 기능인 tool, 맥락으로 읽는 자료인 resource, 다시 쓰는 틀인 prompt다. server를 연결할 때는 이 가운데 무엇을 어떤 역할로 쓸지 정해 둔다. client 쪽 요소인 elicitation은 server가 사용자에게 추가 정보나 확인을 요청하는 통로이므로, 사람이 확인해야 하는 일은 이 통로로 묻는다.

세션·하네스·샌드박스

Anthropic의 Managed Agents는 세션(session)을 사건의 append-only log로, 하네스(harness)를 모델을 부르고 도구 호출을 넘기는 loop로, 샌드박스(sandbox)를 실행 환경으로 정의한다. 부록 B에서는 이 세 역할을 작은 연구 작업 공간의 파일에 대응시킨다. 세션에서 확인한 내용은 project-memory.json과 기록 장부에 남긴다. 하네스 규칙은 AGENTS.md와 프롬프트 템플릿에 담고, 저장소·데이터셋·결과물과 명령 실행은 샌드박스에서 다룬다. 첫 AI 세션에서는 이 세 경계를 먼저 밝히고 행동 하나만 선택한다. 앞의 기본 용어 표에서 말한 하네스는 이 loop에, 무엇을 읽고 실행하고 확인한 뒤 어떤 주장을 허용할지 정한 규칙까지 더한 것이다.

작업 절차를 skill로 구성하는 기준

한 가지 작업에만 쓰는 절차는 폴더 하나로 떼어 AGENTS.md 옆에 둔다. Anthropic은 Agent Skills를 지시·스크립트·자료를 담은 폴더로 설명한다. 에이전트는 정해진 작업을 더 잘하려고 이 폴더를 찾아 필요할 때 불러 쓴다. SKILL.md는 YAML frontmatter로 시작하며, name과 description은 필수다. description에는 이 절차를 언제 여는지 적는다. 부록 B의 「첫 연구 루프는 하나만 고른다」 표에서 상황 칸에 적힌 '논문 한 편을 읽는다' 같은 문장이 여기에 해당한다. 단계적 공개(progressive disclosure)에서는 단계마다 읽는 양이 다르다. 1단계에서는 이름과 description만 system prompt에 올리고, 2단계에서는 관련 있다고 판단하면 SKILL.md 본문을 읽으며, 3단계에서는 같은 폴더의 다른 파일을 필요할 때 읽는다. 폴더가 여러 개여도 1단계에 올라가는 것은 이름과 description뿐이다.

부록 B — 첫 연구 작업 공간 만들기

본문에서 AI가 잘하는 일과 틀리는 일, 사람이 감당할 위험, 하네스가 확인할 경계를 먼저 읽는다. 그런 다음 이 부록에 모아 둔 파일을 새 연구 작업 공간으로 옮긴다.

도구의 역할부터 나눈다

처음에는 연구가 지금 어디까지 왔는지와 도구마다 맡길 역할을 정한다. 어떤 모델을 쓸지는 그다음에 정한다. 역할을 먼저 정해 두면 그 역할을 맡는 제품은 나중에 바꿔도 된다.

연구 장면 먼저 열 도구 첫 확인
저장소를 읽고 작은 수정을 한다 코딩 에이전트 AGENTS.md와 원본 파일을 먼저 읽었는가
논문 주장을 코드와 실험에 연결한다 대화 모델 또는 코딩 에이전트 논문-코드-실험 표가 남는가
ROS2, Docker, CUDA, 데이터셋 오류를 좁힌다 코딩 에이전트와 터미널 단계별 명령 출력이 있는가
외부 저장소나 논문을 찾는다 브라우저·검색 도구 출처 URL과 주장 범위가 분리됐는가
원고와 답변서를 고친다 원고 담당 역할 쓸 문장과 보류할 문장이 분리됐는가
반복 실패를 막는다 하네스 담당 역할 실패를 변경 기록이나 반복 확인 사례로 남겼는가

같은 AI 제품이 여러 역할을 맡을 수 있다. 한 요청 안에서 역할이 바뀌면 확인 기준도 다시 적는다.

tool·resource·prompt와 sampling·elicitation·logging의 구분은 부록 A의 「MCP의 tool·resource·prompt」에서 확인한다.

작업 공간을 만들고 파일을 설치한다

역할과 확인 기준은 파일로 남겨야 다음 세션이 이어받을 수 있다. 루트에는 AI가 먼저 읽을 파일을 두고, 나머지는 용도별 폴더로 나눈다.

workspace/
├── AGENTS.md
├── README.md
├── project-memory.json
├── repos/
├── datasets/
├── artifacts/
├── notes/
└── templates/

이 폴더들은 서로 다른 디스크에 둘 수 있다. 동기화 폴더, 외장 디스크, 원격 서버를 쓴다면 Git 메타데이터와 데이터셋을 어디에 저장할지 먼저 정한다. 코드 이력, 원시 데이터, 실험 결과물, 비공개 메모는 처음부터 나누어 둔다.

가이드 묶음의 templates/에 있는 시작 파일은 아래 자리로 복사한다. workspace-readme.md를 README.md로, AGENTS.template.md를 AGENTS.md로, project-memory.template.json을 project-memory.json으로 복사하고, 첫 요청에 쓸 first-ai-session-prompt.md를 notes/에 둔다. 주장과 근거를 적을 claim-evidence-map.md는 원고 작업을 시작할 때 가져온다. README.md에는 이 공간에 무엇을 두는지와 공개·비공개 경계를 어디에 긋는지만 짧게 채운다. 상태 메모는 project-memory.json의 항목에 맞춰 쓴다.

notes/first-ai-session-prompt.md의 Prompt To Send 블록에 세션·하네스·샌드박스 경계를 적는다. 빈칸을 모두 채운 뒤 artifacts/first-ai-session-message.txt에 저장하고, 첫 AI 세션에는 이 파일의 내용을 그대로 입력한다.

AGENTS.md에 프로젝트 규칙을 적는다

루트의 README.md와 AGENTS.md에도 같은 빈칸이 남아 있다. README.md에는 프로젝트 이름과 저장소, 데이터셋, 결과물 위치만 직접 적는다. 이어서 루트의 AGENTS.md에서 다음 항목만 먼저 채운다. 원래 서식은 templates/AGENTS.template.md에 있다.

  • project truth
  • public/private boundary
  • managed agent boundary
  • work modes
  • evidence gate
  • durable corrections

이미 CLAUDE.md, .claude/, Cursor 규칙이 있다면 옮길 규칙과 버릴 명령을 나눈다. 따라 할 절차는 templates/codex-porting-checklist.md에 있다. 파일 이름과 플러그인 명령은 도구마다 형식이 다르므로 규칙의 의미부터 본다. "가정을 드러내라", "작게 고쳐라", "성공 기준을 검증 가능하게 만들어라" 같은 규칙은 Codex에서도 그대로 쓴다.

한 작업에서만 쓰는 절차를 skill 폴더로 떼는 기준은 부록 A의 「작업 절차를 skill로 구성하는 기준」에서 확인한다.

현재 상태를 먼저 기록한다

AGENTS.md의 project truth와 durable corrections에 채울 내용은 여기에서 나온다. 프로젝트 목표, 지금 정본으로 삼는 코드 경로와 dataset, 실험과 원고의 진행 정도, 심사에서 문제가 될 만한 부분, 계속 적용할 교정 사항을 원본 파일과 실행 결과로 확인한다. 확인한 내용은 상태 메모에 적는다.

첫 AI 요청은 한 작업으로 좁힌다

첫 요청에는 적어도 아래 항목을 넣는다. 답하기 전에 하는 전체 점검은 부록 C의 점검 항목으로 따로 한다. 첫 요청은 templates/first-ai-session-prompt.md를 채워 보낸다. 가장 작은 형태는 이렇다.

Read AGENTS.md and the first-day workspace checklist.
Before answering, state:
- object under truth control
- current evidence permits
- current evidence forbids
- smallest next action
- verification
Do not infer project truth from summaries when source files or artifacts are
available.

AI의 답을 연구 작업에 쓰기 전에 그 근거부터 확인한다. 첫 메시지는 artifacts/first-ai-session-message.txt처럼 파일로 남겨 두고, 다음 세션도 같은 읽기 순서로 시작한다.

첫 연구 루프는 하나만 고른다

project-memory.json의 first_research_loop에 고정할 루프를 여기에서 고른다.

상황 시작 템플릿
논문 한 편을 읽는다 paper-code-experiment-map.md
데이터셋 상태가 불명확하다 dataset-archaeology-sheet.md
실험 숫자를 해석한다 experiment-contract.md
오류를 좁힌다 stage-local-debugging.md
원고 문장을 고친다 claim-evidence-map.md

한 번에 여러 루프를 열면 요청이 다시 넓어지므로 첫 요청의 성공 기준은 하나만 둔다. 표에서 「논문 한 편을 읽는다」 줄을 골랐다면 이렇게 요청한다. "이 논문의 핵심 주장, 실제로 호출되는 코드 경로를 확인할 대상, 실험 절차의 빈칸을 분리하라."

세션을 닫기 전에 결과를 기록한다

작업이 끝나면 project-memory.json이나 weekly-research-ledger.md에 현재 확인한 사실, 아직 말하면 안 되는 주장, 다음 행동 하나를 적는다. 다음 세션이 이 세 줄을 어떻게 읽고 이어 가는지는 부록 D에서 다룬다.

AI가 잘못된 가정을 세웠다면 그 사례를 notes에 적어 두고, 같은 가정이 반복되면 AGENTS.md의 규칙 한 줄로 올린다. 다음 세션은 이렇게 남긴 기록을 읽고 시작한다.

세 줄 가운데 아직 말하면 안 되는 주장은 claim_boundaries에 옮긴다. 첫 세션이 끝난 뒤 project-memory.json의 current_evidence, first_research_loop, claim_boundaries, next_smallest_actions를 함께 고친다. 이렇게 고쳐 두면 다음 AI 세션이 같은 근거 범위를 이어받는다.

부록 D — 다음 세션으로 이어지는 연구 기록

AI와 연구할 때는 다음 세션이 앞서 확인한 근거 안에서 작업을 이어 가도록 기록을 남긴다. 파일과 명령, 숫자, 원고 문장이 어디에서 나왔는지도 함께 적는다.

다시 시작할 때 필요한 기록

  • AGENTS.md
  • 현재 상태와 계속 적용할 사용자 교정 사항을 적은 프로젝트 기억 기록
  • 공개/비공개 경계
  • 지금 이어 갈 작업 하나
  • 다음 AI 요청에서 확인해야 할 항목

작업 공간을 다시 열었을 때 확인했다고 말할 수 있는 상태는 아래와 같다.

workspace can be resumed
first research loop is selected
next small action is known

아직 말하면 안 되는 내용도 적어 둔다.

method works
experiment improved
reviewer risk is resolved

작업에 맞는 결과물을 남긴다

한 번의 작업에서는 중심 결과물 하나를 정한다. 논문을 읽었다면 주장, 코드 경로, 실험 조건을 정리한 표가 중심 결과물이다. 남길 파일과 확인할 항목은 무엇에서 시작했느냐에 따라 다르다.

ROS 2에서 자주 막히는 문제

QoS 불일치로 토픽이 오지 않을 때

ROS2의 기본 publisher·subscription profile의 reliability는 RELIABLE이고, sensor data profile의 reliability는 BEST_EFFORT다. 카메라나 LiDAR driver가 sensor data profile로 보내는데 subscriber가 기본 profile로 받으려 하면 reliability가 맞지 않아 둘은 처음부터 연결되지 않는다. 토픽이나 driver를 의심하기 전에 실제 QoS부터 확인한다.

# 토픽의 QoS 프로파일 확인
ros2 topic info /camera/image_raw --verbose

출력에서 Reliability: BEST_EFFORT, Durability: VOLATILE 같은 줄을 확인한 뒤 subscriber의 QoS를 맞춘다.

from rclpy.qos import QoSProfile, ReliabilityPolicy, DurabilityPolicy

qos = QoSProfile(
    reliability=ReliabilityPolicy.BEST_EFFORT,
    durability=DurabilityPolicy.VOLATILE,
    depth=10
)
self.subscription = self.create_subscription(Image, '/camera/image_raw', self.callback, qos)

코드를 요청할 때는 "이 토픽의 QoS는 BEST_EFFORT / SENSOR_DATA다"처럼 직접 확인한 profile을 함께 적는다. 코드를 받은 뒤에도 그 값이 들어갔는지 다시 확인한다.

use_sim_time과 tf2의 시간 불일치

rosbag을 --clock으로 재생할 때는 노드의 use_sim_time:=true도 함께 켜야 tf lookup이 bag의 시각을 찾는다. tf2 lookup failed가 나타나면 static_transform_publisher를 붙이기 전에 clock 설정부터 확인한다.

bag 파일의 timestamp는 기록한 시각인데, use_sim_time을 켜지 않은 노드는 현재 시스템 시간으로 tf를 찾는다. bag은 --clock으로 재생해 /clock을 내보내고, 노드에는 use_sim_time을 켠 뒤 실제로 적용됐는지 확인한다.

# bag clock을 publish하는 재생 예
ros2 bag play my_bag --clock

# 노드 실행 시 sim_time 활성화
ros2 launch my_package my_launch.py use_sim_time:=true

# 실제 노드에 적용됐는지 확인
ros2 param get /my_node use_sim_time

tf2 lookup 코드를 받은 뒤에는 timeout과 예외 처리가 포함됐는지 확인한다.

from rclpy.duration import Duration

try:
    transform = tf_buffer.lookup_transform(
        'base_link', 'camera_link',
        rclpy.time.Time(),
        timeout=Duration(seconds=1.0)
    )
except tf2_ros.LookupException as e:
    self.get_logger().warn(f'TF lookup failed: {e}')

ROS 2 작업 공간 소싱 순서

ROS2 workspace에서는 /opt/ros/humble/setup.bash를 먼저 source한 다음 ~/ros2_ws/install/setup.bash를 source한다. 실행 절차를 받으면 그 안에 base와 overlay workspace가 모두 있는지, 불러오는 순서가 맞는지 확인한다.

# base를 먼저, overlay를 나중에 source
source /opt/ros/humble/setup.bash
source ~/ros2_ws/install/setup.bash

.bashrc에 경로를 넣었는데 새 terminal에서 package가 안 보이면 다시 설치하기 전에 source 상태부터 살핀다. echo $AMENT_PREFIX_PATH는 현재 적용된 workspace를 보여 준다.

커스텀 메시지 빌드와 반영

.msg 파일을 만들 때는 CMakeLists.txt와 package.xml의 dependency도 함께 수정한다. 변경안을 받은 뒤에는 두 파일이 모두 포함됐는지 확인한다.

rosidl_generate_interfaces 설정이 빠지면 build는 통과하지만 Python import에서 막힌다. 이때는 package 설치를 살피기보다 interface 생성 설정을 먼저 확인한다.

# CMakeLists.txt에 반드시 추가
find_package(rosidl_default_generators REQUIRED)
find_package(std_msgs REQUIRED)
find_package(geometry_msgs REQUIRED)

rosidl_generate_interfaces(${PROJECT_NAME}
  "msg/MyCustomMsg.msg"
  DEPENDENCIES std_msgs geometry_msgs
)

<!-- package.xml에 반드시 추가 -->
<buildtool_depend>rosidl_default_generators</buildtool_depend>
<exec_depend>rosidl_default_runtime</exec_depend>
<depend>std_msgs</depend>
<depend>geometry_msgs</depend>
<member_of_group>rosidl_interface_packages</member_of_group>

--symlink-install을 붙여 build해야 Python 코드 수정이 바로 반영된다. 고친 코드가 그대로 옛 동작을 보이면 build option을 먼저 확인한다. cache는 그 뒤에 살핀다.

# Python 패키지 수정이 바로 반영되려면
colcon build --symlink-install

# 토픽 목록부터 확인하라

# 특정 패턴으로 필터링

디버깅을 요청할 때는 ros2 topic list와 ros2 node list 출력을 함께 보낸다. 두 출력이 있어야 namespace 문제와 node 문제를 구분할 수 있다.

ROS 2 launch 파일

에이전트가 만든 ROS2 Python launch 파일에서는 다음을 확인한다.

  • ROS1 XML 문법과 ROS2 Python 문법의 혼용
  • 노드 의존성을 놓친 LaunchDescription action 순서
  • ComposableNode와 일반 Node의 혼동
  • multi-robot 구성에서 PushRosNamespace 누락

multi-robot 구성에서는 GroupAction 안에 PushRosNamespace를 넣어 노드마다 namespace를 붙인다.

# multi-robot launch 파일에서 네임스페이스 적용
from launch.actions import GroupAction
from launch_ros.actions import Node, PushRosNamespace

robot1_group = GroupAction([
    PushRosNamespace('robot1'),
    Node(package='my_pkg', executable='my_node', name='sensor_node'),
])

에이전트에게 launch 파일을 요청할 때는 ROS2 Python 형식인지, multi-robot namespace가 필요한지, ComposableNode를 쓸지를 적어 준다.

Docker에서 자주 빠지는 설정

Docker GUI와 디스플레이 권한

Docker 안에서 RViz나 Gazebo 같은 GUI 도구를 띄울 때 X11이나 XWayland를 쓰려면 display socket과 인증을 넘겨야 한다. xhost +local:docker는 local X server를 모든 로컬 사용자에게 열어 주므로, 필요한 socket만 골라 넘긴다.

다음은 X11 socket을 넘기는 최소 예다. X server 인증 정보는 host 설정에 맞춰 따로 넘긴다. 접근 제어는 켠 상태로 둔다.

docker run -it \
  --env DISPLAY=$DISPLAY \
  --env QT_X11_NO_MITSHM=1 \
  -v /tmp/.X11-unix:/tmp/.X11-unix:rw \
  my_image

위 옵션과 함께 볼 설정은 다음과 같다.

  • QT_X11_NO_MITSHM=1 — Docker 안에서 MIT-SHM(공유 메모리) 확장 때문에 RViz가 죽으면 이 확장을 끈다.
  • --ipc=host가 있어야 도는 프로그램도 있지만, 이 옵션은 host의 IPC namespace를 공유한다. 오류를 재현해 확인한 뒤에만 붙인다.
  • Wayland session에서는 X11 socket mount 외에 추가 설정이 필요할 수 있다. 로그인할 때 Xorg session을 고르거나 host의 XWayland·Wayland 권한 설정에 맞춘다. XDG_SESSION_TYPE 환경 변수를 바꿔도 현재 실행 중인 display server는 그대로다.

USB 장치 연결

카메라, LiDAR, IMU 같은 USB 장치를 Docker 안에서 쓰려면 device를 하나씩 지정해 매핑해야 한다. 드라이버를 다시 설치하기 전에 container 안에 device가 보이는지 확인한다.

# 필요한 디바이스만 매핑
docker run -it --device=/dev/ttyUSB0 --device=/dev/video0 my_image

# 모든 디바이스 접근 허용 (보안상 비추, 디버깅용으로만)
docker run -it --privileged my_image

Docker 문서에 따르면 --privileged는 모든 host device 접근과 확장된 capability를 컨테이너에 부여한다. 상시 운용에서는 필요한 device만 --device로 매핑한다.

container를 띄운 뒤 꽂은 USB 장치는 기존 device mapping 밖에 있다. 이때는 container를 다시 띄우거나, 디버깅할 때만 --privileged와 -v /dev:/dev를 함께 쓴다.

Docker의 ROS 네트워크

Docker 컨테이너 간 ROS2 통신에서 --network=host는 설정이 단순하지만 host의 network namespace를 공유해 network isolation을 없앤다. 포트 충돌 여부와 네트워크가 열리는 범위를 함께 확인한다.

bridge network에 있는 ROS2 노드들이 서로를 찾지 못하면 DDS(Data Distribution Service) discovery에 쓰이는 multicast가 container 경계를 넘는지 확인한다. Docker bridge 설정에 따라 discovery packet이 container 안에 갇힐 수 있다.

# 가장 간단한 방법 (개발 환경에서)
docker run -it --network=host my_ros2_image

# ROS_DOMAIN_ID로 다른 사람과 충돌 방지
docker run -it --network=host -e ROS_DOMAIN_ID=42 my_ros2_image

같은 네트워크에서 ROS_DOMAIN_ID가 겹치면 다른 시스템의 ROS2 graph와 연결된다. 연구실에서 여러 명이 동시에 ROS2를 쓰면 서로의 토픽이 보인다.

DDS를 더 세밀하게 조정해야 할 때는 Cyclone DDS config XML에 쓸 네트워크 인터페이스를 하나만 적는다. 현재 Cyclone DDS 설정 문서는 인터페이스를 General/Interfaces 아래 NetworkInterface로 적는다.

<!-- cyclone_dds.xml -->
<CycloneDDS>
  <Domain id="any">
    <General>
      <Interfaces>
        <NetworkInterface name="eth0"/>
      </Interfaces>
    </General>
  </Domain>
</CycloneDDS>

사용할 config 파일은 환경 변수로 지정한다.

export CYCLONEDDS_URI=file:///path/to/cyclone_dds.xml

Docker 안팎의 파일 소유권

root 사용자로 실행한 Docker 컨테이너에서 만든 파일은 host에서 root 소유로 남아 고치거나 지우려면 sudo를 써야 한다. 호스트 사용자의 uid·gid로 container를 띄우면 소유권이 그대로 따라온다.

# 호스트 사용자 권한으로 실행
docker run -it --user $(id -u):$(id -g) my_image

--user 옵션으로 호스트 사용자 권한을 적용해도 장치나 directory 권한 때문에 ROS package가 동작하지 않을 수 있다. 이때는 chmod 777로 모두 열기보다 Dockerfile에 non-root user를 만들고 필요한 group과 directory 권한만 준다.

# Dockerfile에서 non-root 유저 설정
RUN useradd -m -s /bin/bash rosuser && \
    usermod -aG dialout rosuser
USER rosuser

센서·하드웨어·실시간 조건

시리얼 포트 권한

/dev/ttyUSB0에 연결할 때 Permission denied가 나타나면 sudo chmod 666 /dev/ttyUSB0으로 일시적으로 접근할 수 있다. 다만 이 권한은 재부팅하거나 장치를 다시 연결하면 사라진다.

다시 연결해도 남는 설정은 udev rule로 만든다.

# 벤더/프로덕트 ID 확인
udevadm info -a -n /dev/ttyUSB0 | grep -E 'idVendor|idProduct'

# /etc/udev/rules.d/99-sensors.rules
SUBSYSTEM=="tty", ATTRS{idVendor}=="1546", ATTRS{idProduct}=="01a9", GROUP="dialout", MODE="0660", SYMLINK+="gps"

# udev rule 적용
sudo udevadm control --reload-rules && sudo udevadm trigger
sudo usermod -aG dialout "$USER"  # 다시 로그인한 뒤 group 적용

이렇게 하면 해당 USB 장치는 /dev/gps라는 고정 이름으로 연결되고 권한도 함께 적용된다. 같은 모델을 여러 개 쓸 때는 시리얼 번호를 규칙에 넣어 서로 구분한다.

USB 대역폭

USB3 카메라 여러 대를 같은 허브에 연결했을 때 프레임이 끊기면 driver와 함께 USB 컨트롤러의 대역폭도 확인한다.

# 어떤 카메라가 어떤 USB 컨트롤러에 붙어있는지 확인
lsusb -t

컨트롤러 대역폭이 원인이라면 설정보다 배선을 바꾼다. lsusb -t의 Bus 번호를 보고 카메라를 서로 다른 USB 컨트롤러에 나누어 연결한다. 데스크톱 PC에서는 앞면과 뒷면 포트가 서로 다른 컨트롤러에 연결돼 있기도 하다.

LiDAR의 IP와 UDP 연결

Velodyne이나 Ouster LiDAR에서 데이터가 들어오지 않을 때는 드라이버를 다시 설치하기 전에 네트워크 설정부터 확인한다. 고정 IP와 subnet이 맞지 않아도 같은 증상이 난다.

많은 Ethernet LiDAR는 고정 IP나 지정된 subnet 설정을 사용한다. 장치가 예를 들어 192.168.1.201/24라면 host interface도 겹치지 않는 192.168.1.x/24 주소로 맞춘다. 실제 주소와 UDP port는 장치 설정과 제조사 문서를 따른다.

# 1단계: LiDAR에 ping이 되는지 확인
ping 192.168.1.201

# 2단계: 호스트 이더넷 인터페이스 IP 설정
sudo ip addr add 192.168.1.100/24 dev eth0
sudo ip link set eth0 up

# 3단계: UDP 패킷이 오는지 tcpdump로 확인
sudo tcpdump -i eth0 udp port 2368 -c 10

장치가 ICMP에 응답하면 ping으로 연결을 확인한다. ICMP를 막아 둔 장치라도 Wireshark나 tcpdump로 지정된 UDP port에 패킷이 들어오는지 살핀다. 패킷은 들어오는데 ROS 토픽이 비어 있으면 드라이버와 ROS 설정으로 확인 범위를 좁힌다.

카메라 드라이버와 v4l2

간단한 예제는 cv2.VideoCapture(0)만 보여 준다. 하지만 USB 카메라 하나가 영상과 메타데이터용으로 /dev/video0, /dev/video1을 함께 만들기도 하므로 장치 번호를 먼저 확인해야 한다.

# 카메라 디바이스 매핑 확인
v4l2-ctl --list-devices

# 지원하는 포맷과 해상도 확인
v4l2-ctl -d /dev/video0 --list-formats-ext

# 이 장치가 지원하는 control 확인
v4l2-ctl -d /dev/video0 --list-ctrls

자동 노출(auto exposure)과 자동 화이트밸런스가 frame 사이의 밝기를 크게 바꾸면 특징점 추출과 추적이 흔들린다. control 이름과 값의 허용 범위는 driver와 kernel 버전마다 다르므로 --list-ctrls 출력에서 먼저 확인한다. 아래 예는 현재 Linux kernel의 이름이고, 예전 kernel에서는 exposure_auto, exposure_absolute처럼 다른 이름으로 나온다.

# 수동 노출 설정 (SLAM용)
v4l2-ctl -d /dev/video0 --set-ctrl=auto_exposure=1
v4l2-ctl -d /dev/video0 --set-ctrl=exposure_time_absolute=100

# 화이트밸런스 고정
v4l2-ctl -d /dev/video0 --set-ctrl=white_balance_automatic=0

SLAM이 흔들리면 알고리즘 매개변수를 만지기 전에 자동 노출과 화이트밸런스를 고정해 본다. 그 상태에서 영상 밝기와 특징점 추출이 안정되는지 함께 확인한다.

Jetson의 ARM·JetPack 환경

에이전트가 만든 코드나 Docker 설정에는 x86을 전제로 한 의존성이 섞이기도 한다. NVIDIA Jetson에서는 ARM64와 JetPack의 버전 제약을 함께 확인한다.

주의할 점:

  • package와 version의 조합에 따라 ARM64 wheel이 없을 수 있다. 이때는 source build로 가기 전에 JetPack package, NVIDIA container, 배포판 package 가운데 맞는 배포물이 있는지 찾아본다.
  • JetPack 버전은 CUDA, cuDNN, TensorRT의 호환 범위를 정한다. 개별 패키지를 최신 버전으로 올리기 전에 JetPack 호환표를 읽는다.
  • Docker image는 장치의 L4T·JetPack release와 호환되는 ARM64 image를 고른다. NVIDIA JetPack release notes에서 현재 조합을 먼저 확인한다.

장치에 설치된 조합은 이렇게 확인한다.

# L4T release 확인 (JetPack 버전은 이 L4T 번호로 NVIDIA 표에서 찾는다)
cat /etc/nv_tegra_release

# NVIDIA 문서의 r36.3 예시. 실제 장치에서는 확인한 L4T와 맞는 tag를 선택
docker pull nvcr.io/nvidia/l4t-jetpack:r36.3.0

코드를 요청할 때는 "Jetson Orin, JetPack 5.1.2, CUDA 11.4 환경이다"처럼 장치에서 직접 확인한 조합을 적는다. 이 숫자는 적는 형식을 보이기 위해 든 예다.

실시간 제어 주기

time.sleep(0.01)은 최소 대기 시간을 준다. 루프가 다시 도는 시점은 계산 시간과 운영체제 스케줄링이 정한다.

# 주기 검증이 필요한 단순한 구현
import time
while True:
    do_control()
    time.sleep(0.01)  # 실제 주기는 계산 시간과 시스템 부하에 따라 달라진다

Python의 GIL(Global Interpreter Lock)과 운영체제 스케줄링도 멀티스레드의 실행 시점에 영향을 준다. 엄격한 실시간성이 필요하다면 C++과 RT(Real-Time) 커널(PREEMPT_RT) 같은 구성을 살펴본다.

# 실제 퍼블리시 주파수 확인
ros2 topic hz /cmd_vel

코드에 적은 주파수는 목표다. ros2 topic hz가 출력하는 숫자는 관측된 수신 주파수다. 두 숫자가 벌어지면 계산 시간, 스케줄링, 통신 지연을 차례로 확인한다.

반복 실패의 원인을 좁히는 법

시뮬레이션에서만 동작하는 경우

Gazebo에서 동작한 코드가 실제 로봇에서 실패한다면 시뮬레이션과 현실이 다른 지점을 확인한다.

  • 센서 노이즈: 시뮬레이터에 넣은 노이즈 모델이 실제 센서의 분포와 어긋난다
  • 통신 지연: 시뮬레이션과 실제 시스템의 transport·queue·network 지연이 다르다
  • 타이밍 불일치: 시뮬레이터의 clock·timestamp 조건과 실제 센서 간 동기화 오차가 다르다
  • 좌표계 불일치: URDF와 실제 로봇의 센서 위치/각도가 미세하게 다르면 tf가 틀어진다

에이전트에게 질문할 때도 "시뮬레이션에서 성공한 동작이 실제 로봇에서 실패한다. 센서 노이즈 수준은 X다. 통신 지연은 Y ms다. 좌표계는 Z 방법으로 보정했다"처럼 측정한 차이를 숫자로 적어 준다.

소프트웨어를 고치기 전에 하드웨어부터 확인한다

케이블 불량, 접촉 불량, 전원 부족은 로그와 장치 상태를 직접 확인해야 구분할 수 있다. 센서 데이터가 간헐적으로 끊길 때는 버퍼 크기, 타임아웃, QoS와 함께 케이블과 USB 허브의 전원도 확인한다.

# 커널 로그에서 하드웨어 문제 단서 찾기
dmesg | tail -20

# USB 연결 해제/재연결 이벤트 확인
dmesg | grep -i usb | tail -20

dmesg에 USB disconnect, device descriptor read/64, error -71 같은 줄이 보이면 연결 상태와 전원부터 확인한다. 케이블을 바꾸고, 전원을 따로 받는 USB 허브를 연결하고, 다른 포트에 꽂아 증상이 달라지는지 비교한다.

OpenCV 재설치 전 패키지·ABI 충돌 확인

라이브러리 버전이 충돌한다면 환경 전체를 다시 설치하기 전에 pip show package_name으로 버전을 확인하고, 어느 패키지끼리 충돌하는지부터 좁힌다.

OpenCV에서는 다음 패키지가 한 환경에 섞이면 충돌할 수 있다.

  • opencv-python (기본)
  • opencv-python-headless (GUI 없는 서버용)
  • opencv-contrib-python (추가 모듈이 든 것)
  • cv_bridge (ROS 패키지, 자체 OpenCV를 참조)

세 PyPI package는 같은 cv2 namespace를 차지하므로 한 환경에는 하나만 둔다. cv_bridge는 system OpenCV와 연결될 수 있어 pip OpenCV를 섞으면 version·ABI 충돌이 생길 수 있다. 현재 적용된 ROS package와 Python import 경로를 확인한 뒤 한 배포 경로를 고른다.

# 현재 설치된 OpenCV 확인
pip show opencv-python opencv-python-headless opencv-contrib-python

# ROS Humble system package 상태와 실제 import 경로 확인
apt policy ros-humble-cv-bridge
python3 -c 'import cv2; print(cv2.__version__, cv2.__file__)'

ROS Humble의 system OpenCV와 ros-humble-cv-bridge를 쓰기로 했다면 import 경로가 그쪽을 먼저 가리키게 둔다. package를 지우기 전에는 그 package에 의존하는 프로젝트가 있는지 확인한다.

반복 처방을 멈추고 원인을 추적한다

같은 처방을 되풀이해도 증상이 그대로라면 한 층 아래에서 원인을 관측한다. 시스템 로그를 확인하고, strace로 호출을 따라가며, 필요하면 패킷을 잡는다.

에이전트에게 물을 때는 에러 메시지뿐 아니라 다음과 같은 저수준 정보도 함께 보낸다.

# 시스템 로그
dmesg | tail -30
journalctl -u my_service --since "5 minutes ago"

# 프로세스 추적
strace -f -e trace=open,openat,read,write ros2 run my_pkg my_node 2>&1 | head -100

# 네트워크 패킷 캡처
sudo tcpdump -i eth0 -w capture.pcap

이 정보를 함께 주면 에이전트가 현재 시스템에서 얻은 증거로 원인을 좁힐 수 있다.

부록 G — Claude의 Adaptive thinking과 Prompt caching (2026년 10월)

Claude 문서에 나온 버전과 수치를 정리해 둔다. 아래 항목의 확인 날짜는 2026년 10월 23일이다. 모델과 제공 플랫폼에 따라 지원 범위와 요금이 다르므로, 코드를 바꿀 때는 링크한 문서의 해당 모델 항목을 다시 확인한다.

Adaptive thinking

이전에는 답변 전에 모델이 쓸 thinking 분량을 thinking: {"type": "enabled", "budget_tokens": N}으로 직접 정했다. extended thinking 문서에 따르면 Claude 4.6 모델에서는 이 방식이 deprecated지만 요청은 아직 처리된다. Claude 4.7 이상 모델은 이 방식을 지원하지 않고 400 오류를 돌려준다. thinking을 지원하는 Claude 4.5 이하 모델에서는 이 방식만 쓸 수 있다.

이제는 thinking: {"type": "adaptive"}를 쓴다. 모델은 요청마다 thinking을 쓸지, 쓴다면 얼마나 쓸지 스스로 정한다. 깊이는 budget_tokens 대신 output_config의 effort로 조절한다. 실제 사용량은 응답의 usage.output_tokens_details.thinking_tokens에 나온다.

앞 턴의 thinking block을 다음 턴까지 남기는지는 모델마다 다르다. thinking 문서에 따르면 Opus 4.5 이후 Opus 모델, Sonnet 4.6 이후 Sonnet 모델, Haiku 5.5, Fable 5.1, Mythos 5.1, Fable 5, Mythos 5, Mythos Preview는 앞선 모든 턴의 thinking block을 기본으로 남긴다. 남은 block은 입력 토큰으로 청구된다. 그보다 앞선 Opus·Sonnet 모델과 Haiku 4.5까지의 Haiku 모델은 마지막 턴의 block만 남기고 나머지는 API가 지운다. prompt caching 문서에 따르면 이 모델들은 도구 결과가 아닌 새 사용자 메시지가 들어오면 앞의 thinking block을 지우고, 그 뒤 메시지의 캐시도 무효가 된다.

Prompt caching

호출할 모델을 고정해도 요청의 어느 부분을 바꾸는지에 따라 비용은 달라진다. prompt caching 문서에 따르면 요청의 앞부분이 같으면 캐시에 저장된 부분을 다시 계산하지 않고 그대로 쓴다.

캐시는 tools, system, messages 순서로 쌓인다. 앞쪽이 바뀌면 뒤쪽 전체를 다시 쌓아야 한다. 예를 들어 도구 정의 하나를 고치면 캐시 전체가 처음부터 새로 저장된다. thinking 설정이나 effort 값을 바꿔도 messages 캐시는 무효가 된다.

저장 요금과 읽기 요금은 따로 매긴다. 5분 동안 저장할 때는 기본 입력 요금의 1.25배, "ttl": "1h"로 한 시간까지 늘리면 2배다. 캐시에서 읽어 올 때는 대체로 0.1배다. Claude Opus 5.5와 Claude Sonnet 5.5는 0.05배, Claude Fable 5.1과 Claude Mythos 5.1은 0.025배다. 무효가 된 구간을 다시 캐시에 저장하면 저장 요금이 다시 붙는다.

캐시가 적용되는 최소 토큰 수도 모델마다 다르다. Opus 5.5, Opus 5, Sonnet 5.5, Haiku 5.5는 512, Sonnet 5는 1,024, Haiku 4.5는 4,096이다. 이보다 짧은 앞부분은 저장되지 않아 매번 다시 계산된다.
